# 日志与错误诊断

框架模块、服务端业务代码和浏览器代码统一使用 `core.logger`。用 `core.logger.child({ module, scope })` 标记稳定的来源，英文日志消息说明发生的操作。应用与常规 CLI 操作沿用 Core 日志配置，应用可通过 `_core.yml` 的 `logging.level` 或 `HAI_CORE_LOGGING_LEVEL` 设置阈值。提供 JSON 输出的命令按其机器可读输出契约处理诊断。

## 日志级别

| 级别 | 使用场景 |
| --- | --- |
| `trace` | 请求和响应摘要、循环细节等按需诊断。请求查询只记录参数数量。 |
| `debug` | 常规读写的安全摘要、预期的 HTTP 4xx、客户端对已带服务端追踪编号的错误进行关联。 |
| `info` | 初始化完成、服务就绪和有意义的低频状态变化。 |
| `warn` | 模块所拥有的业务操作失败、可恢复的外部故障或清理失败。 |
| `error` | 初始化或连接失败、影响资源状态的关闭失败、未预期异常和服务端 5xx。 |
| `fatal` | 进程无法继续运行的故障。 |

由能看到根因的层记录失败。上层复用错误码和追踪编号，按需要补充诊断摘要。接口和 UI 使用现有的公开错误映射与本地化提示。客户端自己的网络、协议或未处理异常需要独立诊断。操作日志的读写开关控制正常摘要，错误日志由对应级别和 Core 阈值控制。持久化审计遵循审计契约。

## 保留根因与关联信息

- 对 `HaiResult` 先判断 `success`。业务调用方应得到有区分度的错误码和消息，以及可获得的原始 `error.cause`。把后续失败单独保存在 `error.ext.cleanupError` 等既有诊断字段，保留取消原因和业务分支所需的错误码。HTTP 对外使用安全消息和追踪编号。
- 日志使用结构化上下文。沿用模块已有的操作名和错误码字段，并按需记录失败阶段、状态和可用的 `traceId` 或 `requestId`。上游请求编号独立记录为 `providerRequestId`。需要堆栈时保留可排查的脱敏异常链。
- 用明确的字段白名单构造日志。省略密码、token、密钥、连接凭据、完整配置、请求正文和查询值、联系方式、消息主题和正文、签名 URL、对象或文件内容、SQL 绑定值、文档、向量和过滤值。连接地址复用 `core.sanitize.sanitizeUrl`。字段脱敏不能识别自由文本里的全部私密值，外部错误正文应提取有界的错误码、状态和请求编号。

## Storage

`storage` 默认开启写操作摘要，读操作按需开启。常规操作使用 `debug`，上传、下载、删除等失败返回业务错误并记录 `warn`，初始化、连接或关闭失败记录 `error`。日志省略对象键、签名地址和内容。使用 `HAI_CORE_LOGGING_LEVEL`，旧的 `HAI_STORAGE_OPERATIONLOG_LEVEL` 与 `operationLog.level` 已移除。

流式上传保留源读取错误、取消原因和 S3 原始写入错误。分片清理也失败时单独保留清理错误，并记录可用的 S3 操作名和请求编号。条件写入冲突按 `ALREADY_EXISTS` 处理。使用 Storage 时查阅项目中 `hai-storage` 的配置与错误说明。

## 验证

修改日志或错误处理时，从实际公共入口验证受影响的成功和失败分支。按场景核对日志级别、原始原因、关联编号和脱敏字段。涉及上传、取消或回滚的双重失败，用受控故障验证业务结果和日志均保留首次错误与清理诊断。可使用 `core.logger.observe` 捕获结构化记录。
