# 任务文档范本

默认使用 `docs/task-list.md` 和 `docs/tasks/T001-<slug>.md`。已有项目优先沿用现存清单及命名；多份独立计划使用 `docs/<plan>-tasks.md`、`docs/tasks/<plan>-T001-<slug>.md`，避免编号碰撞。编号在计划内稳定，文件名与分支不随标题修改。根据真实内容替换下列示例字段，不把未发生的结果写成事实。

清单承担全局状态与需求覆盖，任务文件承担当前验收和每轮证据。适用字段保留，简单项目无需另建规格副本、设计文档层、JSON 状态文件或专用脚本。规划时写概要，执行时补证据；不能预填 Red 成功、合并 SHA 或“已完成”。

- 执行范围：<仅规划 / 全部依次实施 / 用户指定的编号>
- 拆分依据：<为什么一个任务或按这些功能边界拆分，及实际先后依赖>
- 整体验收：<全量门禁命令、关键业务流程与必要环境>

| 编号 | 可验收结果 | 来源 | 依赖 | 分支 | 状态 | 任务记录 |

## 单任务记录

```markdown
# T001 · <可验收结果>

- 清单：[任务清单](../task-list.md)
- 当前状态：待执行
- 分支：codex/<plan>/t001-<slug>；主分支：<实际名称>
- 需求来源：<文档相对链接、精确章节/编号与版本>
- 前置依赖：<编号、已合并契约/提交；无则写无>
- 范围：<本任务交付什么；与相邻任务的边界>
- 复用与影响：<已有框架/应用能力、真实缺口及代码/配置/调用方/文档位置>

## 验收与验证

- <明确输入/角色/操作 → 可观察结果，适用权限与异常边界>
- <适用测试入口、门禁命令、必要环境；UI 流程与截图要求>

## 第 1 轮 · 首次实施

- 起点：<主分支 SHA 与本轮需求版本>
- Red：<用例位置、命令、目标失败原因与实际结果/证据>
- Green / Refactor：<最小实现、测试结果与证据>
- 同步：<代码、配置、迁移、权限、i18n、README 和受影响调用方的实际更新>
- 任务门禁：<命令、结果、日志/截图位置；未运行原因>
- 实现提交/分支 tip：<通过后填入 SHA>
- 合并：<实际 merge SHA；合并前写尚未合并>
- 集成验证：<主分支上的命令、结果及证据>
- 下一步/阻塞：<可直接恢复的具体步骤>
```

返修在同一任务文件追加下列内容；顶部状态、当前验收和清单同步更新，上一轮事实保留。

```markdown
## 第 2 轮 · <返修原因>

- 关联：<第 1 轮实现/merge SHA、用户反馈或缺陷位置>
- 基线与变化：<本轮主分支 SHA、需求修订及规则差异>
- 影响：<依赖任务、配置/数据兼容与需要回归的调用方>
- Red：<新增复现用例、命令、目标失败与证据>
- Green / Refactor：<修复与结果>
- 同步与门禁：<实际修改文件、命令和证据；未运行原因>
- 实现提交/分支 tip：<本轮 SHA>
- 合并与集成验证：<新的 merge SHA、主分支结果>
- 下一步/阻塞：<具体步骤>
```

## 常见请求

- “根据 docs/需求.md 生成代码”：审查当前版本，形成清单，在已授权范围内依次实施。
- “只分析文档并拆分任务”：生成清单与任务概要，不开始实现或合并。
- “执行 T003”：先核验其依赖与当前状态，只实施指定任务。
- “继续上次任务”：从清单和 Git 事实恢复当前阶段，补齐中断的验证或合并记录。
- “T002 有问题，修复后合并”：复用原编号、文件和分支，追加返修轮次并关联此前合并。
