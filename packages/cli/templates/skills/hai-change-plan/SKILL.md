# 变更影响与方案确认

## 能力契约

| 项目 | 契约 |
| --- | --- |
| 能力 | 将框架变更整理成维护者看得懂、能作决定的方案，并跟踪同步与验证 |
| 适用场景 | 新增、修改、删除框架功能，或修复中发现需要改变结构、配置、核心流程、模块边界 |
| 输入 | 用户目标、当前实现与调用方、现有配置和文档、已确认方案及授权 |
| 输出 | 简明方案、具体影响、用户决定、同步清单和验证结果 |
| 限制 | 未确认的重要变更先停在方案；普通业务私有实现不因此扩大成框架改造，已确认且未扩大的方案不重复确认 |

## 何时先提方案

发现以下任一实际变化，在修改对应实现、配置或模板之前说明方案，**等待用户明确同意推进**：

- `type`、`interface`、Schema 等结构的字段、形状或语义改变，包括新增、删除及会改变执行方式的内部结构。
- 模块配置或环境变量的名称、位置、默认值、可选/必填、校验、优先级、安全含义改变。
- 初始化/关闭、请求处理、认证授权、数据读写、并发重试、部署/恢复等核心流程改变。
- 模块职责、依赖关系、公开入口、调用方式或跨模块返回值/错误契约改变。

先查源码、调用方和运行证据，给出足以决定的具体方案；不要只说“重构一下”“优化架构”。只读分析、现状复现及不改变上述边界的准备工作可以继续，不能先落地再要求追认。已有“修复”“按最佳方案”等一般授权，不代替尚未说明的重要方案；用户已明确指定并同意的具体方案无需重问。执行中出现新的重要影响，只确认新增部分。

纯格式、注释纠错、翻译修正，或不改变上述结构与边界的内部修复，按已有授权继续；先简述实际影响即可。拿不准时说明具体不确定项，不为假设风险引入审批。

## 怎样说明

先用一两句话说明结论，再按实际复杂度交代：

1. **为什么改、改成什么**：当前场景有什么问题，使用前后有什么变化。
2. **影响谁**：涉及哪些模块、应用、CLI 模板和调用方；旧配置、数据、部署是否需要调整。
3. **如何同步与验证**：需要更新哪些文档、注释、示例与测试；如何确认生效，失败如何恢复。
4. **请用户决定**：给出推荐方案；确有取舍时列少量可行选项，并说明代价。

技术名词和必要路径用于支持判断，避免堆文件清单与过程日志。简单变化一小段即可，复杂变化再分层。区分已确认事实、待验证假设、拟实施及已完成；明确哪些部分尚未获准，不把等待写成完成。

## 确认后成套维护

在当前任务记录中保存决定和影响范围，不额外创建重复台账。按[沟通与同步维护](../hai-app-create/collaboration.md)逐项核对相关 README（已有中英日版同步）、环境变量与模块配置项、`docs/` 使用说明、GitHub Pages 的内容源/导航/图片、注释与类型说明、调用方、测试和 CLI 模板。每项注明已同步，或不适用及原因。

GitHub Pages 由文档源构建时修改源文件，不手改生成产物；配置示例按真实默认值与覆盖顺序核对，界面截图来自当前实际操作。按受影响范围验证，报告实际执行、复用与未验证边界。若实现与获准方案不同，先说明差异并重新确认新增影响。
