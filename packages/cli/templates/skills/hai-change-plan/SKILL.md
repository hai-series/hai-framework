# 变更影响与方案确认

## 能力契约

| 项目 | 契约 |
| --- | --- |
| 能力 | 识别须人工确认的变更，说明具体方案与影响，确认后实施和验证 |
| 适用场景 | 框架、应用及 CLI 模板的开发、修复、重构、升级和迁移 |
| 输入 | 用户目标、当前实现与调用方、现有配置和文档、已确认方案及授权 |
| 输出 | 简明方案、具体影响、用户决定、同步清单和验证结果 |
| 限制 | 规定范围内的变更须在实施前取得人工明确确认。同一方案及影响已获确认时沿用该决定 |

## 哪些变更必须人工确认

新增、修改或删除涉及下列任一项时，**先说明具体方案及影响，等用户明确确认后再实施**。规则同时适用于框架、应用私有实现和 CLI 模板，改动大小、任务名称和可行方案数量均不影响触发。

- **配置项**。配置文件、环境变量或代码内配置的键名、路径、取值、默认值、必填性、类型、校验、优先级和生效方式，包括仅修改一个环境的取值、模板默认值或依赖升级带来的默认值变化。
- **功能点及输入输出**。模块下任何 `<模块名>.xxx` 功能（含多级入口，如 `core.config.load`）以及应用功能、API 和 CLI 命令的增删改。核对参数、字段、单位、校验、返回值、错误、事件、副作用和实际行为，签名相同也要检查。
- **核心实现逻辑**。业务规则、关键算法、状态流转、初始化与关闭、认证授权、数据读写与事务、并发与重试、部署与恢复等。即使公开接口及数据结构保持一致，也须确认核心逻辑改法。
- **数据表及缓存结构**。表、列、类型、约束、索引、默认值及迁移方式，以及缓存键、前缀、数据类型、值结构、序列化、过期与失效规则。单项字段、索引或键规则变化也适用。
- **类型和模块边界**。`type`、`interface`、Schema 等的字段、形状或语义，包括影响执行的内部结构，以及模块职责、依赖关系、公开入口或调用约定。

当实际改动均未触及上述范围时，纯文档、格式、注释、翻译等改动，以及保持这些边界的非核心内部修复，按已有授权推进。

## 实施前核对确认

1. 先查源码、调用方及运行证据，逐项识别本次触发的变更。用当前行为、拟改方案、改后行为和实际影响说明需要决定的内容，点明受影响的环境、调用方、已有数据和兼容成本。按需补充迁移、恢复和验证方式。只有一种可行方案时也提交该方案请用户决定。
2. 确认须来自用户，能从会话或任务记录核实，且明确对应本次的具体方案及影响范围。用户此前已明确确认同一方案及影响时，记录依据后继续。一般性的“修复”“按文档实现”“直接升级”、模板默认值、AI 建议、自动审批、测试通过和用户未回复均不能当作该确认。
3. 确认前将相关部分停在方案。只读分析、复现现状和已授权且独立于该决定的工作可继续。获得确认后才修改对应代码、配置、模板、迁移和定义新行为的目标测试，或执行会落地这些改动的命令。
4. 执行、排错或验收时发现拟改方案或实际影响超出已确认范围，先停下对应部分，说明差异并取得新增或变更部分的确认。其余已确认范围按原决定推进。

简单变更用一小段说明即可。确有取舍时列出可行选项及代价，可将多项具体决定一次提交给用户，记录用户确认的范围。

## 确认后成套维护

在当前任务记录中保存决定和影响范围，不额外创建重复台账。按[沟通与同步维护](../hai-app-create/collaboration.md)逐项核对相关 README（已有中英日版同步）、环境变量与模块配置项、`docs/` 使用说明、GitHub Pages 的内容源/导航/图片、注释与类型说明、调用方、测试和 CLI 模板。每项注明已同步，或不适用及原因。

GitHub Pages 由文档源构建时修改源文件。配置示例按真实默认值与覆盖顺序核对，界面截图来自当前实际操作。按受影响范围验证，报告实际执行、复用与未验证边界。提交或交付前用实际差异复核每项确认，发现缺少依据时标出对应变更并暂停该部分交付。
