## 1. 启动和使用性能

一次本地 Podman 冷任务验收中，三种真实 Agent 分别通过同一 `scoped.run` 访问隔离网络里的模型夹具。Codex 3.73 秒、DSH 3.61 秒、Goose 2.94 秒，各 1 次，包含任务提交、启动、一次模型请求和回收。模型为本地夹具，这组数字用于核对链路，生产时延需另测。

修复前，Hai 只在创建会话时给 Codex 注入提供方配置。App Server 仍使用默认提供方刷新远程模型目录，导致 `thread/start` 和随后 `model/list` 各可能等待约 5 秒。修复后，App Server 在启动时读取独立的 `CODEX_HOME/config.toml`。[完整源码与对照](acp-startup-investigation.md)

| 原始对照 | 修复前配置 | 启动前加载提供方 |
| --- | ---: | ---: |
| 断网 session/new，每组 3 次 | 中位 10,032 ms，10,015–10,063 ms | 中位 15 ms，10–26 ms |
| 真实 DeepSeek session/new，每组 5 次 | 中位 7,375 ms，2,656–7,984 ms | 中位 23 ms，11–54 ms |
| 真实网关首次 thread/start + model/list | 2,959 + 5,009 ms | 11 + 1 ms |
| 最后一组短回答的 prompt 首字，各 1 次 | 10.30 秒 | 5.89 秒 |
| 同一 prompt 完成，各 1 次 | 10.39 秒 | 5.95 秒 |

原始对照使用 `.env.local` 指定的 `deepseek-flash` 和真实 DeepSeek Responses 接口，两组回答均正确。默认目录认证使用占位 key，真实 key 只发给 DeepSeek。按正式配置重新测试 3 次，新建会话耗时分别为 21.20、9.97、9.70 ms。同轮短答首字为 984 ms，完成耗时 1063 ms，各 1 次。首字计时从发出 prompt 起算，并排除模型元数据警告。[正式配置复测](acp-startup-investigation.md#6-正式代码与验收)

| 用户场景 | 需要等待什么 | 当前可用评估 |
| --- | --- | --- |
| 热 session 续聊 | prompt + 模型 + 工具 | 无需重新启动 Worker 或新建 session |
| 热 Worker 新对话 | session/new + 模型 | 优化探针新建 11–54 ms；0.1 秒内可作本地准备候选目标 |
| 镜像已缓存，启动新 Worker | 容器、原生程序、握手、新建 session | 旧环境分段实测推算的本地准备预算 0.6–1.5 秒，尚非 ai.acp 全流程测量 |
| 本地没有镜像 | 拉取、校验、解压，再执行上一步 | 未实测；缓存大小和有效带宽决定下限 |
| 工程/MCP/长历史 | Git/依赖、工具初始化、历史加载 | 未测，不使用空会话数据承诺 |
| 调用独立工具 | 工具排队、准备/预热命中、执行、产物传输 | 本地缓存镜像的小文件作业见下表。Office 已验证预热复用与产物发布，端到端延迟仍待测 |

分段数据来自前轮缓存镜像实验：容器创建启动约 298 ms，exec 约 146 ms；Agent 握手在不同组为 170–241 ms。它们不是一次完整请求中的独立统计分布，不能相加后宣称 P95。新 minimal 镜像及新增授权入口、调度和工具代理会改变结果，需要完整链路复测。

用户总等待应记录为：排队 → 拉镜像/准备资料 → Worker 启动 → session 新建/恢复 → 模型首字 → 工具与最终结果。审批等待单列；待审批会话仍可能保留 Worker 内存，不能把它算成资源已完全释放。

分布式还需分别记录提交入库、执行节点领取、控制请求路由、首个持久事件到客户端的耗时。轮询间隔决定空闲时的领取延迟，事件合并会增加少量首字等待；未测前不承诺具体毫秒数。先测单节点与至少两个 API/执行节点的同任务对照，再决定是否需要额外通知组件。热 session 续聊也要计入路由/持久化开销，不等同于直接连接原生进程。

### 独立工具的本地耗时

在 rootless Podman 6.1.4 下，每次用已缓存镜像创建一个禁网容器，限额为 1 vCPU、1 GiB、128 PID。每个操作预跑一次，再串行记录 5 次 `podman run --rm` 耗时并校验输出。夹具为 1–6 KiB 的小文件。数字包含容器创建、挂载、工具执行和销毁。

| 操作 | 中位数 | 最快–最慢 |
| --- | ---: | ---: |
| DOCX、XLSX、PDF 提取 | 分别 256、241、276 ms | 231–270、192–261、222–284 ms |
| Office 转 PDF | 1,159 ms | 1,083–1,170 ms |
| Office 重算 XLSX | 1,131 ms | 1,075–1,307 ms |
| OCR 单张 700 × 160 PNG | 327 ms | 305–407 ms |

三个镜像执行空操作时，同一容器生命周期的中位数为 203–222 ms。测试未覆盖数据库、MCP、对象存储、排队、镜像下载或预热命中，生产评估应分开记录这些阶段。原始数据保存在本机 `tmp/acp-generalization-20261113/tool-cached-elapsed.json`。

小文档样本为 100 段 Word、2,000 行 × 10 列 Excel、10 页文本 PDF；输入约 36 KiB、67 KiB、3 KiB。读取后三份内容生成并重新打开 Word，校验段落、表格总和及 PDF 文本；无图片、复杂版式、公式重算和 OCR。每种方式 20 次：

| 同一脚本的运行方式 | 墙钟中位 | CPU 中位 |
| --- | ---: | ---: |
| 直接 Python | 235.4 ms | 235.1 ms |
| 常驻 App Server，外层容器 | 244.2 ms | 245.0 ms |
| 再加 Codex 内层沙箱 | 279.4 ms | 280.4 ms |

单 Python 子进程峰值 RSS 最大约 55.75 MiB。内层沙箱在该样本增加约 35.2 ms 墙钟和 35.4 ms CPU；不能由此决定关闭生产隔离。独立工具服务的常驻进程、传输和作业启动不包含在直接 Python 数字里。

500 次这种小文档脚本约需 118 CPU 秒，16 个充分利用的核的理想计算下限约 7.4 秒；不含模型、I/O、排队和新工具池开销。复杂附件可能远超此量级，须按文件种类分别测试。

镜像层在同一节点共享，不按容器数重复计算；多个可选镜像按实际共享层计算，不能把完整镜像大小简单相加。还需单独计历史、附件、输出、工作树、依赖缓存、工具临时盘、预热可写层和升级旧版本。库未加载不自动占同量 RAM，但预热进程会占内存。

例如假设压缩传输量 500 MiB，有效带宽 100 Mbit/s，仅传输约 42 秒；1 Gbit/s 约 4.2 秒，还需校验解压。这是算术例子，不是当前镜像实测下载量。

## 3. 500 个任务不等于 500 个同时运行

假设 100 人每人同时提交 5 个独立任务，每任务占活动名额 20 秒，环境已热、没有模型限流：

| 分配 | Worker | 活动任务 | 全部完成的理想时间 |
| --- | ---: | ---: | ---: |
| shared：1 个 Worker、1 个名额 | 1 | 1 | 10,000 秒，约 167 分钟 |
| shared：25 个 Worker、每个 4 个名额 | 25 | 100 | 100 秒 |
| user：100 个用户、每人 1 个名额 | 100 | 100 | 100 秒 |
| task：每批准入 100 个任务 | 至多 100 | 100 | 100 秒，另加批次准备 |
| task：全放行 | 500 | 500 | 20 秒，资源要求最高 |

这些是单次 run 任务的队列算术，不是吞吐验证。shared 四会话并行和所有 Agent 的并发边界还需验收；同一 session 的连续消息始终串行。user 每人开两个名额时尾批只有一个任务，完成时间是 60 秒，不能假设一直满载。持续交互的 task session 在两轮之间可能仍保留独占 Worker，必须另计空闲存活数，不能只按正在生成的任务数估算内存。

工具队列、模型额度和执行资源都会成为瓶颈。等待工具的原生 prompt 通常仍保留活动会话及内存，不在没有证明卸载/恢复机制时将其扣除。

## 4. 加入独立工具池后的内存预算

建议同时维护两张账：**按实测负载估算的常见占用**，以及**准入时承诺的资源上限**。前者用于选型和优化，后者决定最多启动多少环境。

已有 Codex 测量：单 Worker 空会话 PSS 约 192–194 MiB；8 个同容器 Worker 各约 88–98 MiB，受共享代码页分摊影响；本次真实短回答后的快照约 161–182 MiB。它们不代表长历史、并发任务或 cgroup 峰值。RSS/PSS/cgroup 不能混成一个“每 Worker 固定占用”，也不能据此给 DSH/Goose 设置相同最小内存。

### 4.1 常见占用的规划示例

以下是以 Codex 快照为参考的假设：每 Worker 基础 192 MiB，每活动任务另留 96 MiB，平台/系统/工具入口共 4 GiB。4 GiB 是单机综合预算占位，包含同机 API/runner、连接/事件缓冲及基础服务，不是逐项实测结果。工具池按独立执行环境总数计入：

| 工具池 | maxRunning / maxTotal | 单环境内存上限假设 | 最多计入 |
| --- | --- | ---: | ---: |
| 小文档 | 16 / 16 | 256 MiB | 4 GiB |
| Office | 2 / 2 | 1 GiB | 2 GiB |
| OCR | 2 / 2 | 1 GiB | 2 GiB |
| 合计 | 20 / 20 | — | 8 GiB |

这里 maxTotal 包含启动中、预热、运行和清理中的环境；满额时不额外补预热。可配置空闲时文档预热 2 个、Office 预热 1 个，预热目标不能突破 maxTotal。这是容量示例，与运行设计中的“Office 最多 4 个活动作业”示例不是同一部署。

新公式：`(W × 192 MiB + A × 96 MiB + 8 GiB 工具池 + 4 GiB 平台系统) / 0.75`。25% 留空是初始规划，96 MiB 活动增量和工具限额均待实测。

| 配置 | 规划内存 | 负载压测起点，不是峰值保证 |
| --- | ---: | --- |
| 25 shared Worker / 100 活动任务 | 34.8 GiB | 16 vCPU / 48–64 GiB |
| 100 user 或 task Worker / 100 活动任务 | 53.5 GiB | 16 vCPU / 64 GiB；严格不超配时看下一表 |
| 100 user Worker / 500 活动任务 | 103.5 GiB | 24–32 vCPU / 128 GiB，先验证五会话并行 |
| 500 task Worker / 500 活动任务 | 203.5 GiB | 多节点 256 GiB 起测，各节点另算固定开销 |

较上一版 45.5 GiB 的 100 Worker 示例，增加到 53.5 GiB，是因为文档池从 2 GiB 改为 4 GiB，并新增 Office/OCR 各 2 GiB，合计多 6 GiB，再除以 0.75。不是新实测发现 Agent 变重。

### 4.2 不超配时按硬上限预留

若要求每个已准入任务都能同时达到其内存上限，还需更高预算。例如轻量独占 Worker 每个上限 512 MiB，多会话 Worker 每个 1 GiB，加上述 8 GiB 工具池和 4 GiB 固定开销：

| 部署 | 按限额预留并保留 25% 后 |
| --- | ---: |
| 25 shared Worker × 1 GiB | 49.3 GiB，建议至少 64 GiB |
| 100 独占 Worker × 512 MiB | 82.7 GiB，建议从 96 GiB 起测 |
| 100 多会话 Worker × 1 GiB | 149.3 GiB，建议从 160–192 GiB 起测 |
| 500 独占 Worker × 512 MiB | 349.3 GiB，多节点逐机预留 |

这只是内存保证示例，1 GiB 能否承载某 Agent 的 4/5 个真实会话仍待验证。64 GiB 节点按此规则留下 25% 空余，扣除工具和固定预算后只能准入约 72 个 512 MiB Worker；想运行 100 个，要增加内存、降低经过验证的每实例限额，或显式接受超配及降载策略。

CPU 也要区分资源预留和限速上限。前表 16/32 vCPU 是网络等待较多场景的起测规格，不保证 100 个容器同时各获得 1 CPU。CPU 密集任务按总 CPU 预算准入；磁盘、PID、网络和 GPU 同样独立核算。任务 container 内执行的文档脚本若已计在 Worker 峰值里，不再重复计进独立工具池；真正两处都运行则两处都计入。

混合 Agent 部署改为逐类求和：`Σ(该 Agent Worker 数 × 实测基础占用 + 活动任务数 × 实测增量) + 工具池 + 各节点固定开销`。严格准入仍按已批准的容器上限逐节点预留。分布式 API/执行副本各有运行开销，数据库主备、连接池、对象存储、日志/事件保留、镜像重复缓存和网络带宽单独预算；不能把单机 4 GiB 固定项原样套到整个集群。

要承受一台执行节点退出，还需预留其可接管负载的容量，并满足镜像/架构/工作区条件；总空闲内存足够不代表每台节点都能放下目标任务。多个环境有碎片时会先排队。节点故障后有未知副作用的任务仍需核对，不把备用容量当作自动重复执行的许可。

## 5. 模型额度与收费调用

每任务平均占活动槽 S 秒，调用模型 q 次，累计 K token：持续 A 并发约需 `60 × A × q / S` RPM 和 `60 × A × K / S` token/分钟。

例如 S=20、q=1、K=5000：100 并发需要约 300 RPM/150 万 token 每分钟；500 并发约 1500 RPM/750 万 token 每分钟。一次性 500 任务的一批总量是 500 请求/250 万 token，与持续满载速率不同。工具回合、历史重发、图像、重试和额外 RAG 模型调用另计。

增加 Worker 或工具副本不能突破供应商额度。模型额度按实际凭据、模型和租户分配，接近限额时排队或降并发，不通过自动重复付费调用掩盖失败。

## 6. 上线前必须补测什么

1. 每个 Agent × 支持环境的镜像压缩/展开大小、缓存/无缓存启动、原生握手和真实 prompt，记录镜像/模型版本。
2. 原生多 session 顺序和并行、关闭与恢复、长历史、MCP 初始化、技能加载；至少数百次有效样本后再讨论 P95/P99。
3. 文档、Office、OCR、浏览器分别测 cold/warm、产物校验和真实复杂输入；不能拿 235 ms 小脚本代表整个服务。
4. 至少两个入口节点和多个执行实例，覆盖 100 用户 × 5 任务、取消、重连、OOM、失租、规则撤销和模式切换；测整个节点与 cgroup 的峰值，以及任务领取/事件转发/数据库的延迟和负载。
5. 实测资源到达上限后的排队、拒绝、清理和公平性，确认没有孤儿进程、重复外部操作或跨用户产物。
