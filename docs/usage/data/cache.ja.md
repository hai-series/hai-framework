## それぞれの記録の役割

まず用途と例を読み、必要に応じて後半の項目・保存規則を確認してください。ID と業務内容は架空で、秘密は隠しています。時刻は 2026-11-17 00:00 UTC を起点とし、単位は各説明に記します。

### 一時的な数値

対応する構造：`orders:total`。

業務の数値を一時保存し、同時更新には原子的な計数操作を使います。

```json
3
```

total は業務で付けた名前で、3 はその計数です。Cache 全体のキー数ではありません。

### 資料の一時保存

対応する構造：`orders:profile:42`。

取得済みの資料を次のリクエストで再利用します。変更時は業務側で更新・削除します。

```json
{
  "id": "user-42",
  "name": "Example"
}
```

user-42 の例です。ex:60 なら60秒で失効し、期限を付けなければ自動失効しません。

### 項目ごとの資料更新

対応する構造：`orders:profile-fields:42`。

Hash は一項目だけを変更する用途です。

```json
{
  "name": "Example",
  "status": "active"
}
```

name と status は別項目ですが、期限は Hash 全体にかかり、status だけは失効させられません。

### 処理順を持つ一覧

対応する構造：`orders:queue`。

List は順番を保ち、同じ値も複数入れられます。

```json
[
  "order-42",
  "order-43"
]
```

order-42 が先です。これだけでは一度だけの実行を保証せず、永続タスクには Runner 等を使います。

### 重複しないメンバー

対応する構造：`orders:tags`。

Set は存在確認に使い、同じ値を追加しても一つだけ残します。

```json
[
  "new",
  "paid"
]
```

new と paid を含み、表示の配列順は保証されません。

### 点数順のメンバー

対応する構造：`orders:scores`。

ZSet は数値順の一覧や順位表に使います。

```json
[
  {
    "member": "user-42",
    "score": 8
  }
]
```

user-42 の点数は8で、出現回数ではなく並び順の基準です。

### 短時間のロック所有者

対応する構造：`orders:__lock:invoice-42`。

競合する処理を一時的に待たせ、更新・解放には所有者の証明が必要です。

```json
"<lock-token:redacted>"
```

値は秘匿した所有者トークンで、既定は30秒です。最終書き込みの版や一意制約の代わりにはなりません。

## 項目・保存・削除のリファレンス

業務キーと値はアプリで管理します。名前空間と有効期限を明示してください。メモリー方式のデータは終了や再起動で消えます。

| テーブル・キー・成果物 | 形式と管理元 |
| --- | --- |
| `kv`, `hash` | 呼び出し側のキー。JSON またはフィールドと値の対応。カウンターは数値。 |
| `list`, `set_`, `zset` | 重複を許す順序付きリスト、一意な集合、または数値スコア付き集合。 |
| `__lock:<key>` | 所有者のトークン。有効期限でリースが解放され、明示的な解放には同じリースのトークンを使う。 |
