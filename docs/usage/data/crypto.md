# @h-ai/crypto 数据结构

<a id="crypto-数据结构"></a>

[English](crypto.en.md) · [日本語](crypto.ja.md)

[数据结构索引](README.md) · [文件配置](../configuration/crypto.md) · [功能说明](../function/crypto.md)

普通的加密、解密、签名和哈希计算不需要保存记录。只有启用 HTTP 传输加密时，服务端才需要记住“这个客户端用哪把公钥”“哪些请求已经用过”，并限制新增记录的速度。这些数据统一保存在 `@h-ai/cache` 中，Crypto 不建数据库表。

## 缓存

下面按一次客户端接入的过程说明。示例只含虚构标识和公开公钥，服务端私钥不写入这些记录。展示的键是传给 Cache 的名字；Redis 中还会加上应用设置的 `keyPrefix`。

启用 HTTP 传输加密时，Crypto 使用以下 4 类缓存。客户端编号和请求编号来自密钥协商及加密请求。多个节点共用同一个后端和前缀时会读取同一份记录。

| 键或类别 | 用途 | 默认有效期与清理 |
| --- | --- | --- |
| [`hai:crypto:transport:cache:client:<clientId>`](#cache-crypto-client) | 按编号找公钥，验证请求并加密响应。 | 默认 3600 秒。读取不续期，到期后重新协商。 |
| [`hai:crypto:transport:cache:request:<clientId>:<requestId>`](#cache-crypto-request) | 标记已经使用过的请求编号。 | 保留到 `issuedAt + 3660000` 毫秒，到期删除。 |
| [`hai:crypto:transport:cache:quota:register`](#cache-crypto-registration) | 核对本周期新增公钥还能登记多少。 | 首次写入起 60 秒。更新计数不续期。 |
| [`hai:crypto:transport:cache:quota:request`](#cache-crypto-request-quota) | 核对本周期还能登记多少个新请求。 | 首次写入起 60 秒。更新计数不续期。 |

<a id="cache-crypto-client"></a>

### 客户端公钥：让服务端认出请求，并把响应发给正确客户端

客户端先通过密钥协商登记自己的公钥，服务端为它分配 `clientId`。之后收到请求，服务端按这个编号找到公钥，用它验证请求签名，也用它加密要发回的响应。

键为 `hai:crypto:transport:cache:client:<clientId>`，值是公钥字符串。例如：

| 值字段 | 类型 | 默认值 | 说明 | 示例 |
| --- | --- | --- | --- | --- |
| 整个值 | `string` | — | 客户端公钥字符串，完整例子见下方。 | `<SM2 public key>` |

```json
{
  "hai:crypto:transport:cache:client:c_example-42": "0432c4ae2c1f1981195f9904466a39c9948fe30bbff2660be1715a4589334c74c7bc3736a2f4f6779c59bdcee36b692153d0a9877cc62a474002df32e52139f0a0"
}
```

这表示 `c_example-42` 已登记，并使用这把 SM2 公钥。公钥本来就可以公开，示例使用的是公开的 SM2 曲线基点；实际客户端会生成自己的密钥对。记录默认保存一小时，允许设置为 1～86400 秒，读取不会延长时间。到期后，客户端需要重新协商；这不等于用户退出登录，登录会话由 IAM 管理。

<a id="cache-crypto-request"></a>

### 已用请求编号：防止同一个加密请求被再次执行

客户端为每次请求生成新的 `requestId`。服务端确认签名、内容和时间都有效后，先登记“这个编号已经用过”，成功登记的请求才进入业务处理。再次收到相同客户端、相同编号的请求时，直接拒绝。即使请求同时到达两台服务，也只能有一台登记成功。

键为 `hai:crypto:transport:cache:request:<clientId>:<requestId>`。值只需要 `true`，因为服务端只关心“有没有用过”，不需要保存请求正文。例如：

| 值字段 | 类型 | 默认值 | 说明 | 示例 |
| --- | --- | --- | --- | --- |
| 整个值 | `boolean` | — | 收到该编号且成功登记时写入 `true`。 | `true` |

```json
{
  "hai:crypto:transport:cache:request:c_example-42:0123456789abcdef0123456789abcdef": true
}
```

这表示客户端 `c_example-42` 的请求 `0123456789abcdef0123456789abcdef` 已经用过，不能再执行。这里的 `true` 不表示业务成功：即使业务后来报错，这个请求编号也不能重新使用。

签发时间为 00:00 的请求，记录保留到 01:01，即 `issuedAt + 3660000` 毫秒。61 分钟覆盖最长 60 分钟的请求有效期和 1 分钟的节点时钟余量。若请求时间领先服务端 30 分钟，记录写入后可保留 91 分钟。Redis 的内存预算应覆盖这个保留窗口，并保护有效标记直到到期。用户重新提交并生成新编号时，订单等业务仍需自己的防重复规则。

<a id="replay-window-upgrade"></a>

#### 升级后启用更长有效期

若计划使用超过旧版上限 600 秒的有效期，先按原配置升级所有节点。旧版写入的防重放记录有各自的过期时间。最后一个旧节点停止受理请求后，等旧节点受理的请求按新有效期也全部到期，再统一调大配置。新有效期设为 3600 秒时，按旧版最大未来容差 300 秒和 60 秒时钟余量计算，可在等待 66 分钟后启用。

<a id="cache-crypto-registration"></a>

### 新公钥计数：防止不断协商把公钥记录堆满

服务端共用 `hai:crypto:transport:cache:quota:register` 这一个计数键，每登记一把新公钥先占一个名额。例如：

| 值字段 | 类型 | 默认值 | 说明 | 示例 |
| --- | --- | --- | --- | --- |
| `used` | `number` | — | 本轮已占用的登记名额，首次写入 `1`。 | `1` |
| `limit` | `number` | `10000` | 本轮登记公钥的上限。默认值来自存储工厂。 | `10000` |

```json
{
  "hai:crypto:transport:cache:quota:register": {
    "used": 1,
    "limit": 10000
  }
}
```

`used: 1` 表示本轮已占用一个登记名额，`limit: 10000` 表示本轮最多 10000 个。名额可能在后续写入失败时仍被占用，因此它是已接纳登记的计数，不是当前有效公钥总数。首次登记开启 60 秒计数周期，到期后重新计数；不是按钟表上的整分重置。达到上限时拒绝新的协商，Serv/Kit 返回 HTTP 503，已有公钥继续有效。

<a id="cache-crypto-request-quota"></a>

### 新请求计数：防止已用编号记录增长过快

服务端共用 `hai:crypto:transport:cache:quota:request` 这一个计数键，限制每轮能接纳多少个新请求编号。例如：

| 值字段 | 类型 | 默认值 | 说明 | 示例 |
| --- | --- | --- | --- | --- |
| `used` | `number` | — | 本轮已占用的请求名额，首次写入 `1`。 | `1` |
| `limit` | `number` | `100000` | 本轮接纳请求的上限。默认值来自存储工厂。 | `100000` |

```json
{
  "hai:crypto:transport:cache:quota:request": {
    "used": 1,
    "limit": 100000
  }
}
```

这表示本轮已经接纳一个新请求，默认最多 100000 个。计数周期同样是从首次写入起 60 秒。已经登记过的编号再次来访，会被识别为重复请求，不再占新名额；同时到达的重复请求可能保守占用多个名额，但仍只有一次能进入业务。名额用完返回 HTTP 503，不删除已有编号来换取新名额。

## 60 秒周期、满额和业务限流是什么关系

这两项是整个应用共用的缓存容量保底，主要防止异常流量把记录写入速度推得过高。它们不是按 IP、用户或接口分配的业务访问额度，不能代替业务限流；业务限流没有触发时，总新增量仍可能先碰到这层保护。

| 记录 | 默认每轮最多新增 | 达到上限后 | 下一轮何时恢复 |
| --- | --- | --- | --- |
| 客户端公钥 | 10000 把 | 新协商返回 503；已登记公钥不删除 | 本轮首次计数起满60秒后 |
| 已用请求编号 | 100000 个 | 新请求返回 503；已用编号不删除 | 本轮首次计数起满60秒后 |

两类计数各自计时。比如登记计数第一次写入在 **00:00:10**，本轮就在 **00:01:10** 到期。即使00:00:30已经用满，也不会提前开启新一轮；到期后的首次登记开启下一个60秒周期。请求计数按自己的首次写入时间计算。

这不是累计总量或同时在线数。第一轮登记10000把公钥，第二轮还能登记10000把；前一轮尚未过期，所以可以同时有20000把有效。公钥默认保存一小时，请求的已用标记按请求时间保存，均与60秒计数周期分开。上限可通过工厂参数调整；把保底值设得过低会让正常业务收到503，调高则必须相应增加 Redis 内存预算，并保留按 IP/用户/接口的业务限流。

## 为什么这些数据不会无限增长

公钥和已用编号都到期自动删除，两个计数键也有 60 秒期限，而且键名固定，不会每分钟再生成新键。有限保存时间配合每轮新增上限，约束了有效记录的数量。默认设置下，可按公钥约 610000 条、已用编号约 1700000 条估算保守上界；实际内存还包括键名、值和后端开销，到期数据也可能稍后才回收。

多台服务必须连接同一个 Redis，使用相同前缀和配额。同一个后端和 keyPrefix 下的 registry 共用这两个计数；不同应用若需要独立预算，应使用不同的 Cache keyPrefix。否则，一台服务无法知道另一个节点已经接纳了哪些请求。Redis 应使用 `noeviction`，内存不足时拒绝写入，不能悄悄挤掉仍有效的已用编号；还需可靠持久化，避免重启或回滚丢失这些标记。缓存故障时拒绝请求，不能把“查不到状态”当成“可以执行”。memory 模式只适合开发和测试。

应用负责 Cache 的初始化和关闭。传输管理器关闭不会清空共享记录；客户端 `destroy()` 只清理本地会话。私钥始终由密钥环或客户端持有。各节点仍需同步时钟，部署按 ±30 秒核对。
