# Crypto のデータ構造

[中文](crypto.md) · [English](crypto.en.md)

[データ一覧](README.ja.md) · [設定ファイル](../configuration/crypto.ja.md) · [API](../function/crypto.ja.md)

通常の暗号化、復号、署名、ハッシュ計算は記録の保存を必要としません。HTTP 通信を暗号化する場合は、クライアントの公開鍵と「使用済みのリクエスト」を覚え、その増加速度を制限します。保存先は `@h-ai/cache` に統一し、Crypto はデータベース表を作りません。

## キャッシュ

接続からリクエスト処理までの順に説明します。例の ID は架空で、公開鍵だけを含み、秘密鍵は含みません。キーは Cache に渡す名前です。Redis 上ではアプリの `keyPrefix` も付きます。

HTTP 通信の暗号化では、次の 4 種類を保存します。クライアントとリクエストの ID は鍵交換と暗号化リクエストから得ます。同じ保存先と接頭辞を使うノードは同じ記録を参照します。

| キーまたは種類 | 用途 | 既定の期限と削除 |
| --- | --- | --- |
| [`hai:crypto:transport:cache:client:<clientId>`](#cache-crypto-client) | ID から公開鍵を探し、要求を検証し応答を暗号化します。 | 既定で 3600 秒。読み取りでは延長されず、期限後は再度鍵交換します。 |
| [`hai:crypto:transport:cache:request:<clientId>:<requestId>`](#cache-crypto-request) | 使用済みのリクエスト ID を記録します。 | `issuedAt + 660000` ミリ秒で期限切れになります。 |
| [`hai:crypto:transport:cache:quota:register`](#cache-crypto-registration) | この期間に登録できる新しい公開鍵の残数を確認します。 | 初回書き込みから 60 秒。加算時は延長しません。 |
| [`hai:crypto:transport:cache:quota:request`](#cache-crypto-request-quota) | この期間に受け付けられる新規リクエストの残数を確認します。 | 初回書き込みから 60 秒。加算時は延長しません。 |

<a id="cache-crypto-client"></a>

### クライアント公開鍵：送信者を確認し、その相手に応答する

鍵交換でクライアントの公開鍵を登録し、`clientId` を発行します。サーバーはこの ID から公開鍵を探し、リクエストの署名検証と応答の暗号化に使います。

キーは `hai:crypto:transport:cache:client:<clientId>`、値は公開鍵の文字列です。

| 値の項目 | 型 | 既定値 | 用途 | 例 |
| --- | --- | --- | --- | --- |
| 値全体 | `string` | — | クライアント公開鍵の文字列。完全な値は下の例です。 | `<SM2 public key>` |

```json
{
  "hai:crypto:transport:cache:client:c_example-42": "0432c4ae2c1f1981195f9904466a39c9948fe30bbff2660be1715a4589334c74c7bc3736a2f4f6779c59bdcee36b692153d0a9877cc62a474002df32e52139f0a0"
}
```

`c_example-42` がこの SM2 公開鍵で登録済み、という意味です。例は公知の SM2 曲線の基点で、実際のクライアントは独自の鍵を生成します。既定で1時間保存し、1～86400秒に変更できます。読み取りでは延長しません。期限後は鍵交換をやり直しますが、IAM のログインセッションが終了したことにはなりません。

<a id="cache-crypto-request"></a>

### 使用済みリクエスト番号：同じ暗号化リクエストを再実行しない

クライアントは毎回新しい `requestId` を付けます。サーバーは署名、内容、時刻を検証後、その番号を使用済みとして記録します。記録に成功したリクエストだけが業務処理へ進みます。同じクライアントと番号が再び届けば拒否し、2台に同時到着しても記録できるのは1台だけです。

キーは `hai:crypto:transport:cache:request:<clientId>:<requestId>`。値は `true` だけです。「記録があるか」が分かれば十分なので、リクエスト本文は保存しません。

| 値の項目 | 型 | 既定値 | 用途 | 例 |
| --- | --- | --- | --- | --- |
| 値全体 | `boolean` | — | リクエスト ID の取得に成功した時に `true` を書き込みます。 | `true` |

```json
{
  "hai:crypto:transport:cache:request:c_example-42:0123456789abcdef0123456789abcdef": true
}
```

`c_example-42` のリクエスト `0123456789abcdef0123456789abcdef` は使用済みで、再実行できないことを示します。`true` は業務成功の意味ではありません。後で処理が失敗しても番号は使い直せません。

00:00 発行のリクエストなら、印は00:11まで、つまり `issuedAt + 660000` ミリ秒まで残します。まだ受理され得る時間をカバーし、その後はリクエスト自体が古すぎるため印を削除できます。許容する未来時刻との差を含め、新規記録の残存時間は最大16分です。容量確保のため早期削除すると再実行を許すおそれがあります。新しい番号での再送には、注文番号など業務側の重複防止も必要です。

<a id="cache-crypto-registration"></a>

### 新しい公開鍵の計数：鍵交換の連続で保存先を埋めない

全サーバーが `hai:crypto:transport:cache:quota:register` を共有し、新規登録前に1枠を確保します。

| 値の項目 | 型 | 既定値 | 用途 | 例 |
| --- | --- | --- | --- | --- |
| `used` | `number` | — | この期間に受け付けた登録数。初回は `1`。 | `1` |
| `limit` | `number` | `10000` | 一期間の登録上限。既定値はストアファクトリーの設定です。 | `10000` |

```json
{
  "hai:crypto:transport:cache:quota:register": {
    "used": 1,
    "limit": 10000
  }
}
```

`used: 1` は今の期間に1枠を使い、`limit: 10000` は最大10000枠であることを示します。後続の書き込み失敗でも枠は消費され得るので、有効公開鍵の総数ではありません。最初の確保から60秒の期間で計数し、時計の毎分ちょうどにはリセットしません。上限では新規鍵交換を HTTP 503 で拒否し、既存登録は残します。

<a id="cache-crypto-request-quota"></a>

### 新規リクエストの計数：使用済み番号が急増しないようにする

`hai:crypto:transport:cache:quota:request` を全サーバーで共有し、新しく受理する番号を制限します。

| 値の項目 | 型 | 既定値 | 用途 | 例 |
| --- | --- | --- | --- | --- |
| `used` | `number` | — | この期間に受け付けたリクエスト数。初回は `1`。 | `1` |
| `limit` | `number` | `100000` | 一期間のリクエスト上限。既定値はストアファクトリーの設定です。 | `100000` |

```json
{
  "hai:crypto:transport:cache:quota:request": {
    "used": 1,
    "limit": 100000
  }
}
```

今の期間に1件を受理し、既定上限は100000件、期間は最初の確保から60秒です。既知の使用済み番号は新たな枠を使わず拒否します。同時の重複は保守的に複数枠を使う場合がありますが、業務へ進めるのは1件だけです。上限時は HTTP 503 とし、既存の印は削除しません。

## 60秒の期間、上限時の動作、業務のレート制限

この2つは記録の急増からキャッシュ容量を守る、アプリ全体の保護枠です。IP・ユーザー・経路ごとの業務利用枠ではなく、それらのレート制限を置き換えません。個別制限が未到達でも全体の新增量でこの保護枠に達する場合があります。

| 記録 | 1期間の既定新增数 | 上限に達したら | 復旧する時刻 |
| --- | --- | --- | --- |
| クライアント公開鍵 | 10000本 | 新規交換は503、既存公開鍵は残す | 本期間の最初の確保から60秒後 |
| 使用済み番号 | 100000件 | 新規要求は503、既存の印は残す | 本期間の最初の確保から60秒後 |

2つの計数は別々に時刻を持ちます。最初の登録が **00:00:10** なら期間は **00:01:10** までです。00:00:30に上限に達しても次の期間は前倒ししません。期限後の最初の登録から新たな60秒が始まり、要求計数も自身の最初の書き込みで決まります。

累計総数や同時接続数の制限ではありません。各期間に10000本ずつ登録すれば、まだ失効していない20000本が同時に有効です。公開鍵の既定1時間や要求番号の保存期限は、この60秒と別です。工場引数で変更できますが、低すぎると通常要求にも503を返し、高くすれば Redis のメモリも増やす必要があります。IP・ユーザー・経路別の制限も続けて使用します。

## データが無限に増えない理由

公開鍵と使用済み番号は期限後に削除され、2つの計数キーも60秒で失効します。キー名は固定で、毎分新しいキーを作りません。保存期間と受理上限で有効記録数を制限します。既定では公開鍵約610000件、使用済み番号約1700000件を保守的な上限として見積もれます。キーや後端のメモリ、期限後の回収遅延も考慮してください。

同じ後端と keyPrefix の registry は計数を共有します。別アプリに独立した枠を持たせる場合は Cache の接頭辞を分けます。同じアプリの全ノードで同じ Redis、接頭辞、上限を使い、他ノードの使用済み番号も確認できるようにします。Redis は `noeviction` とし、メモリ不足では書き込みを拒否します。有効な印を勝手に追い出してはいけません。再起動やロールバックで失わない永続化も必要です。キャッシュ障害時は処理を拒否し、memory は開発とテストに限ります。

Cache の開始と終了はアプリが担当します。管理器を閉じても共有記録は消さず、クライアントの `destroy()` はローカル状態だけを消します。秘密鍵は鍵リングまたはクライアントが保持します。ノードの時計も同期し、展開時は ±30秒以内を確認します。
