## それぞれの記録の役割

### ファイルの基本情報

対応する構造：`FileMetadata`。

一覧や詳細で場所・サイズ・種類を伝え、本文をダウンロードせず確認できます。

```json
{
  "key": "reports/order-42.txt",
  "size": 5,
  "contentType": "text/plain",
  "lastModified": "2026-11-17T00:00:00.000Z",
  "metadata": {
    "orderId": "order-42"
  }
}
```

5バイトのテキストファイルです。lastModified はコードでは Date、JSON では UTC 文字列です。

### 一度の読み取りで開いたオブジェクト

`StorageFileRead` はサーバーで一度の読み取りによって取得します。`reports/order-42.txt` では、`metadata` が上記の 5 バイトのテキストファイルを示し、`stream` から同じオブジェクトの本文を取得できます。アプリは MIME タイプの検証や応答ヘッダーの作成にメタデータを使います。読み取りを終えた場合や本文を読み取らない場合は、`close()` を呼び出してハンドルまたは接続を解放します。

### ファイルの種類と業務属性を保存する JSON ファイル

保存先：オブジェクトと同じディレクトリ内の `.hai-storage-meta/<ハッシュ>.meta.json`。

ローカルのルートが `./data/storage`、オブジェクトキーが `reports/order-42.txt` の場合、内容は `data/storage/reports/order-42.txt` に保存します。アップロード時に指定した MIME タイプとカスタム属性は `data/storage/reports/.hai-storage-meta/<ハッシュ>.meta.json` に保存します。`file.head()` と `file.getStreamWithMetadata()` はこの metadata ファイルを読み取り、これらの属性を返します。内容の例：

```json
{
  "contentType": "text/plain",
  "metadata": {
    "orderId": "order-42"
  }
}
```

この metadata ファイルには `text/plain` とカスタム属性 `orderId: order-42` が入り、本文・サイズ・更新日時は入りません。アップロード時に両方の属性を省略すると、metadata JSON の内容は `{}` になり、アップロードした本文には影響しません。ファイル名は、デバイス ID、inode、作成時刻、更新時刻、サイズから計算した 64 桁の16進 SHA-256 です。この情報で対応する metadata ファイルを特定するため、アプリから手動で名前や内容を変更しないでください。

オブジェクトの上書き後は、置き換え前の metadata ファイルを削除しようとします。オブジェクト削除時も対応する metadata ファイルを削除しようとします。本文の書き込みや削除が済んでいて metadata の削除だけ失敗した場合、操作は成功を返して警告を記録し、古いファイルが残ることがあります。`.hai-storage-meta/` ディレクトリ自体は削除しません。現在のファイルに対応する metadata ファイルが欠落・破損するとファイル属性の読み取りは失敗するため、自由に削除できるキャッシュではありません。

ファイルシステムのスナップショットから復元する際は、本文と `.hai-storage-meta/` を両方保存し、上記5項目が一致するようにします。通常のコピーでは metadata ディレクトリもコピーしていても情報が変わり、`file.head()` が対応するファイルを見つけられないことがあります。別のファイルシステムに移行する際は、移行元への書き込みを停止し、`file.head()` で種類とカスタム属性を、`file.getStream()` で本文を読み取ります。移行先では `file.put()` で書き込み、新しい metadata ファイルを作成します。

Windows では、ローカルファイルを読み取る際に同じディレクトリへ `<ランダムID>.upload.tmp` という一時的なハードリンクを作り、開いた直後にリンクを削除します。ハードリンクは同じファイルの別名で、内容をコピーしません。開いたストリームは元の内容を読み続け、別のリクエストは元のキーを上書きできます。ファイルシステムがハードリンクに対応し、サービスのアカウントがオブジェクトのディレクトリで一時ファイルを作成・削除できる必要があります。一時リンクは業務オブジェクトの一覧には含まれません。

## 項目・保存・削除のリファレンス

オブジェクトは呼び出し側のキーで保存先に置かれます。Storage は SQL テーブルや Redis キーを作成しません。

| テーブル・キー・成果物 | 形式と管理元 |
| --- | --- |
| `key` | オブジェクトパス。UTF-8 で最大 1024 バイト。 |
| `size`, `contentType`, `lastModified` | バイト数、MIME タイプ、保存先が返す更新日時。S3 のアップロード結果にはアプリが成功応答を受け取った時刻が入ります。 |
| `etag` | キャッシュの検証値。ローカルはサイズと更新日時を使用し、S3 はサービスの値を使用。内容の検証には `storage.checksum` を使用。 |
| `metadata` | アップロード時に設定する任意の文字列属性。 |

S3 では本文・MIME タイプ・カスタム属性を設定したバケットに保存し、保持期間と旧バージョンはバケット設定で管理します。有効期間を指定したアクセスリンクも生成できます。ローカルファイルと metadata ファイルの場所は上記の例を参照してください。内部の metadata ファイルやアップロードの一時ファイルは業務オブジェクトの一覧に含まれません。
