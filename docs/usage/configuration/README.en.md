## How settings take effect

In server projects generated by the CLI, `core.init()` reads the `config/` directory. The application validates the settings and passes them to each module. For example, `config/_db.yml` is registered as `db`. A connection opens when the application passes that configuration to `reldb.init()`. Serv and Kit receive their settings when the application creates an HTTP app or request handler. API Client, Crypto, UI, Datapipe, and Capacitor take settings at their call sites. API Contract defines inputs and outputs in code. Build and deploy commands read their sections from `hai.json`.

A framework default applies when the caller omits a value. A generated project can choose a different value in its files. For example, the Feedback configuration schema defaults to `reach`, while its template configures the console. Values in examples are for that scenario. A required value with no default must come from the application or the target environment.

## Check a configuration change

1. Record the behavior to change and find its current file, environment variable, and consuming code.
2. Update the value for the target environment. Check [override order](runtime.md#配置从哪里来) and keep credentials in private environment files.
3. Validate the settings, restart or reinitialize the service as documented, and rebuild the client when changing a value compiled into browser code. Inspect only the fields needed, such as a port or log level.
4. Check success, refusal, and recovery using isolated accounts or data. Schema validation checks names, types and ranges. Connection and behavior require runtime checks.
5. Keep the deployment artifact, migration record, and compatible backups needed for recovery.

Changes to a public setting also need updates to its schema, callers, module guide, templates, and relevant tests. Run `pnpm check:usage-examples` to validate the annotated examples.
