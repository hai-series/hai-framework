## Configuration entry

A standalone API service generated by the CLI loads `config/_serv.yml` with Core and validates it with `ServConfigSchema`. The server passes `http`, `cors`, and enabled `transport` settings to `serv.createApp()`. Transport encryption also needs a server key ring and shared key registry. When enabling A2A or live voice, supply the corresponding AI, IAM, and application authorization dependencies. Pass the resolved `server.host` and `server.port` to `serv.listen()`. [Application factory arguments](../function/serv.en.md#host-options)

When Core loads this configuration, `HAI_SERV_<FIELD_PATH>` can override YAML. For example, `HAI_SERV_HTTP_APIPREFIX` maps to `http.apiPrefix` and `HAI_SERV_TRANSPORT_MAXREQUESTAGESECONDS` maps to `transport.maxRequestAgeSeconds`. Within one source, a whole-object value provides the base and individual fields override it. The process environment takes precedence over mode-specific private, global private, mode-specific public, and base environment files. A setting takes effect when the application loads it and passes it to the consumer. [Configuration sources and precedence (Chinese)](runtime.md#配置从哪里来)

The generated standalone API and Fullstack servers explicitly bind their addresses, ports, API prefixes, proxy and CORS settings, and enabled transport settings in their respective `_serv.yml` files. You can override optional fields through the registered schema. For example, `HAI_SERV_TRANSPORT_ROUTEPLAINTEXTBYTES` accepts a JSON path map. `http.docs.requireAuth` applies when the docs object is enabled. Restart the server after changes and update deployment settings if a proxy route or probe changed.

## Configuration reference

### Listening

| Field | Type and constraints | Default | Purpose |
| --- | --- | --- | --- |
| `server` | Optional object | `{ host: "127.0.0.1", port: 3000 }` | Parsed HTTP listening address and port. |
| `server.host` | Nonempty string | `"127.0.0.1"` | Hostname or IP address. A nonempty `HOST` takes precedence during parsing. |
| `server.port` | Integer from 1 to 65535 | `3000` | TCP port. A valid `PORT` takes precedence during parsing. |

<a id="local-listening-example"></a>

#### Run a local server

Put the following in `config/_serv.yml` and keep any settings your application needs. This binds the instance to loopback port 4100 so it can run beside another development service. A nonempty `HOST` and a valid `PORT` still take precedence.

```yaml schema=@h-ai/serv:ServConfigSchema
server:
  host: 127.0.0.1
  port: 4100
```

Start the application and open `http://127.0.0.1:4100/health`. Expect HTTP 200 at the framework's default health endpoint.

<a id="http-endpoints"></a>

### API, documentation, and probes

| Field | Type and constraints | Default | Purpose |
| --- | --- | --- | --- |
| `http` | Optional object | Defaults in this section and Request access | API, documentation, health, and request access settings. |
| `http.apiPrefix` | Path starting with `/`. Segments allow ASCII letters, digits, underscores, dots, and hyphens. Dot segments and a trailing slash are invalid | `"/api/v1"` | Route prefix for the business API. Set the key exchange path separately with `transport.keyExchangePath`. |
| `http.openapi` | `false` or object | `false` | An object enables the OpenAPI JSON endpoint. |
| `http.openapi.path` | Full path starting with `/` | `"/openapi.json"` | OpenAPI JSON address for clients and tools. |
| `http.docs` | `false` or object | `false` | An object enables the Scalar API documentation page. |
| `http.docs.path` | Full path starting with `/` | `"/docs"` | Documentation page address. The script is served at `_hai/scalar.js` in the same directory. |
| `http.docs.requireAuth` | Boolean | Omit to allow access without authentication | With `true`, the application must establish a verified session. Documentation responses carry `Cache-Control: private, no-store`. A separately enabled OpenAPI JSON endpoint follows its own access policy. |
| `http.health` | `false` or object | `{ path: "/health", readyPath: "/ready" }` | Enables health and readiness probes. Both show that the HTTP application can respond. |
| `http.health.path` | Full path starting with `/` | `"/health"` | Health endpoint. |
| `http.health.readyPath` | Full path starting with `/` | `"/ready"` | Readiness endpoint. |

Use separate paths for the documentation page, OpenAPI JSON, and the Scalar script. The handler rejects same-path conflicts among these resources and with a mounted GET or HEAD contract operation.

Generated projects using `serv.createRuntimeSecurityPolicy()` keep the OpenAPI JSON endpoint and documentation page disabled in production. The Core environment, proxy routes, and probe configuration affect what the deployment exposes. [Deployment and documentation paths (Chinese)](http.md#serv监听和路由)

<a id="docs-health-example"></a>

#### Enable API docs and custom health paths

Put the following in `config/_serv.yml` in development. The docs page requires a verified session provided by the application's authentication flow. Disabling the separate OpenAPI JSON endpoint embeds the specification in the docs page.

```yaml schema=@h-ai/serv:ServConfigSchema
http:
  openapi: false
  docs:
    path: /docs
    requireAuth: true
  health:
    path: /healthz
    readyPath: /readyz
```

Request `/docs` with and without authentication. Expect HTTP 200 and HTTP 401 respectively, with `Cache-Control: private, no-store` on both responses. The default OpenAPI path should return HTTP 404. Check for HTTP 200 from `/healthz` and `/readyz`. To publish OpenAPI JSON separately, use `http.openapi: { path: /openapi.json }` and configure access control for that path.

<a id="request-access"></a>

### Trusted proxies and request access

| Field | Type and constraints | Default | Purpose |
| --- | --- | --- | --- |
| `http.trustedProxies` | `"auto"` or an array of up to 1,000 IPv4/IPv6 addresses or CIDRs | `"auto"` | Accept forwarded addresses only from trusted proxies. `auto` trusts the container subnet on a framework-managed private Compose network. Other deployments ignore forwarding headers by default. `[]` explicitly ignores them. |
| `http.access` | `false`, inline policy object, or separate file object | `false` | Check requests by full path, method, trusted client IP, and time. Inline rules and a file reference are mutually exclusive. |
| `http.access.file` | Path to a regular `.yml` or `.yaml` file, up to 4,096 characters | Required for a file object | Relative to the server process working directory. Read once when assembling the request handler. Maximum file size 1 MiB. |
| `http.access.global` | Inline conditions object | May be omitted | Applies to all requests handled by the current host, including health checks. |
| `http.access.rules` | Array of up to 1,000 path rules | `[]` | A request must satisfy the global conditions and every matching rule. `encryption` can set transport requirements for a matching method and path. |

See the Core request access reference for every field and constraint for time windows, IP lists, paths, HTTP methods, and encryption modes. Kit uses the same policy under `http.access` in `_kit.yml`. [Core request access](core.en.md#request-access) · [Kit request access](kit.en.md#request-access)

<a id="trusted-proxy-example"></a>

#### Allow partner networks to read the report

Partners read the orders console’s external report through a reverse proxy. Merge the settings below into `http` in the configuration file for your server. The proxy connects from `192.0.2.10`, and the partner network is `203.0.113.0/24`. Replace both with the addresses used in your deployment.

```yaml schema=@h-ai/serv:ServConfigSchema
http:
  trustedProxies: [192.0.2.10]
  access:
    rules:
      - id: partner-reports
        paths: [/api/v1/external/reports]
        methods: [GET]
        allowIps: [203.0.113.0/24]
```

Request `GET /api/v1/external/reports` through the proxy from the allowed network. Expect HTTP 200. Repeat from another network and expect 403. If the app is mounted below the origin root, put the full prefixed request path in the rule. To restrict probes, add a separate probe rule or a global policy. [Add partner reports](../getting-started/serv.en.md#orders-console-access)

<a id="time-window-example"></a>

#### Let auditors read reports during working hours

Add this rule to `http.access.rules` with the orders console’s deployed report path. The rule allows requests on weekdays in Shanghai from 09:00 until 18:00, excluding the end time. The report route still checks the existing role and permission.

```yaml schema=@h-ai/serv:ServConfigSchema
http:
  access:
    rules:
      - id: report-hours
        paths: [/api/v1/reports/current]
        methods: [GET]
        timezone: Asia/Shanghai
        windows:
          - days: [1, 2, 3, 4, 5]
            start: '09:00'
            end: '18:00'
```

Sign in as an auditor with `reports:read` and request `GET /api/v1/reports/current` inside and outside that window. Expect 200 inside and 403 on a new request outside it. To let operations manage the policy independently, save the policy object in a separate YAML file and reference it with `http.access.file`. [Separate policy files (Chinese)](request-access.md#4-运维人员携带独立-yaml-交付)

<a id="http-rate-limit"></a>

### Fixed-window rate limiting

| Field | Type and constraints | Default | Purpose |
| --- | --- | --- | --- |
| `http.rateLimit` | `false` or object | `false` | Limit request frequency by trusted client IP. The server supplies the atomic counter store. |
| `http.rateLimit.windowMs` | Integer from 1 to 2147483647, in milliseconds | `60000` | Fixed window starting at the first counter write. Later requests share the same expiration. |
| `http.rateLimit.maxRequests` | Positive safe integer | `100` | Requests a client can pass through the limiter in one window. Excess requests receive HTTP 429. |

Pass the parsed rate-limit settings and an atomic counter store to the request host. Use an in-memory store for single-process development. For multiple instances, use the same Redis, namespace, window, and request budget. By default, counters use the trusted client IP. Requests with no resolved address share the `unknown` counter. Store failures return HTTP 503. HTTP requests that pass the access policy share a budget for each IP. Built-in health and readiness probes and CORS preflights are exempt. Key exchange counts toward the budget when encryption is enabled.

To give each signed-in account its own quota, supply the rate-limit key in the host code. YAML accepts the window and request limit.

<a id="rate-limit-config-example"></a>

#### Limit requests from one client

Put the following in `config/_serv.yml`. The example allows two requests from the same trusted client in 10 seconds. For a self-managed reverse proxy, put the actual proxy IPs or CIDRs in the same `http` object.

```yaml schema=@h-ai/serv:ServConfigSchema
http:
  rateLimit:
    windowMs: 10000
    maxRequests: 2
```

Use `HAI_SERV_HTTP_RATELIMIT` to replace the whole setting or `HAI_SERV_HTTP_RATELIMIT_WINDOWMS` and `HAI_SERV_HTTP_RATELIMIT_MAXREQUESTS` to override the fields.

Start the orders console and request `GET /api/v1/status` three times from the same source within 10 seconds. Expect 200 and 200 with 1 and 0 requests remaining, then 429. Wait the number of seconds shown in `Retry-After` and verify that the next request returns 200. Use the actual bind address and deployment prefix. [Configuration and startup example](../getting-started/serv.en.md#orders-console-access)

<a id="cors"></a>

### Cross-origin access

| Field | Type and constraints | Default | Purpose |
| --- | --- | --- | --- |
| `cors` | `false` or an object | `false` | An object enables CORS using the response and preflight rules below. |
| `cors.origin` | Full origin string, comma-separated string, or string array | `"*"` | Allows browsers to read responses. List explicit origins for credentialed requests. Wildcards cannot be used with credentials. |
| `cors.nativeOrigins` | Comma-separated origins with `http:`, `https:`, `capacitor:`, or `tauri:` schemes | None | Allows additional origins for native apps. |
| `cors.paths` | Array of full request paths | All requests handled by the host | Each item matches that path and its descendants. Include the deployment prefix. An empty array matches nothing. |
| `cors.methods` | Array of HTTP methods | `[GET, HEAD, PUT, PATCH, POST, DELETE, OPTIONS]` | Tells the browser which methods can be used after preflight. |
| `cors.allowedHeaders` | Array of request header names | `[Authorization, Content-Type, X-Requested-With, X-Hai-Reauthentication, X-Hai-Terminal]` | Lists the headers the browser is allowed to send after preflight. |
| `cors.exposedHeaders` | Array of response header names | `[]` | Lets browser scripts read additional headers. The host also exposes `X-Request-Id` and `X-Trace-Id`. |
| `cors.credentials` | Boolean | `false` | Allows cross-origin requests to carry credentials such as cookies. |
| `cors.maxAge` | Non-negative integer in seconds | `86400` | How long a browser may cache preflight results, subject to browser limits. |

With CORS enabled for the path, the host handles preflight for OPTIONS requests bearing `Origin` and `Access-Control-Request-Method`. It checks request access before returning 204 and the preflight consumes no quota. Other OPTIONS requests follow the application route’s access, rate-limit, and transport rules. Generated API Service and Fullstack deployments require explicit Web origins when CORS is enabled in production.

<a id="cors-example"></a>

#### Let the orders console read an API on a separate origin

The console is at `https://console.orders.example.com` and the API is at `https://api.orders.example.com`. Add these fields to the app’s configuration file and substitute the console’s actual origin. These origins share a site, so the browser can send session cookies when their attributes allow it.

```yaml schema=@h-ai/serv:ServConfigSchema
cors:
  origin: https://console.orders.example.com
  paths: [/api/v1]
  methods: [GET, POST, OPTIONS]
  credentials: true
  allowedHeaders:
    - Authorization
    - Content-Type
    - X-Request-Client
    - X-Request-Id
    - X-Hai-Terminal
    - X-Hai-Reauthentication
    - X-Hai-Locale
  exposedHeaders:
    - Retry-After
    - X-RateLimit-Remaining
  maxAge: 600
```

After signing in, use the browser’s Network panel to confirm that API preflights include an `Access-Control-Allow-Origin` matching the console and `Access-Control-Allow-Credentials: true`. When rate limiting is enabled, the console can use `response.headers.get("Retry-After")` on an HTTP 429 to show when another request can be sent. With application-layer transport encryption, add `X-Client-Id`, `X-Encrypted`, and `X-Hai-Transport` to the allowed request headers used by your client, and expose `X-Encrypted` and `X-Hai-Transport`.

### HTTPS for refresh cookies

| Field | Type and constraints | Default | Purpose |
| --- | --- | --- | --- |
| `HAI_SERV_REFRESH_COOKIE_SECURE` | Server process environment variable, exactly `true` or `false` | When omitted, defaults to enabled in production | Controls the `Secure` attribute of enabled refresh cookies. An explicit `refreshCookie.secure` takes precedence. Whole-object `HAI_SERV` overrides do not affect this variable. |

Generated apps use native token transport only when the request matches a configured native origin and passes the application’s other native request checks. [Authentication and guards](../function/serv.en.md#authentication)

<a id="refresh-cookie-secure-example"></a>

#### Sign in over HTTPS and inspect the refresh cookie

If the app enables `refreshCookie`, keep `HAI_SERV_REFRESH_COOKIE_SECURE=true` in the production server environment. Sign in again from the same-site HTTPS console and check that the login or refresh response sets a cookie with `Secure`, `HttpOnly`, and `SameSite=Strict`. Use a cookie-aware API Client to renew the session when the access token expires. This Strict cookie flow requires the two origins to share a site. [Sign in, renew the session, and sign out](../getting-started/serv.en.md#orders-console-iam)

<a id="transport"></a>

### Transport encryption

| Field | Type and constraints | Default | Purpose |
| --- | --- | --- | --- |
| `transport` | `false` or object | `false` | The object configures application-layer transport encryption. Supply a server key ring and shared key registry, and configure the key exchange address on clients. |
| `transport.maxPlaintextBytes` | `"auto"` or an integer from 1,024 to 67,108,864 bytes | `"auto"`, 1 MiB for ordinary routes | UTF-8 plaintext limit for ordinary requests and responses. |
| `transport.maxFutureSkewSeconds` | Integer from 0 to 1,800 seconds | `30` | How far the request timestamp can be ahead of the server clock. |
| `transport.maxRequestAgeSeconds` | Integer from 1 to 3,600 seconds | `300` | How long a request is valid from issuance, including transit time. |
| `transport.routePlaintextBytes` | Up to 100 full paths mapped to integers from 1,024 to 67,108,864 bytes | May be omitted | Limits plaintext in both directions for selected routes. Use the actual request path. `*` matches one complete segment. The smallest matching limit applies. |
| `transport.excludePaths` | Array of full paths starting with `/` | `[]` | Excludes these paths and their subpaths from transport encryption. An explicit `encryption: required` path rule takes precedence. |
| `transport.keyExchangePath` | Absolute path from the origin root | `"/api/v1/_hai/key-exchange"` | Public POST endpoint for key exchange. Path segments may contain ASCII letters, digits, `_`, `-`, and `.`. Dot segments, empty segments, trailing slashes, percent escapes, queries, and fragments are invalid. |

Serve clients over HTTPS. Managed deployments inject `HAI_CRYPTO_TRANSPORT_SERVERKEYRING` privately on the server. Parse and check the ring at startup before setting up the cache-backed transport registry. The browser receives public client settings such as the exchange path. For multiple instances, use a shared registry and consistent time windows. [Key ring configuration](crypto.en.md) · [Wire up the server and browser](../getting-started/serv.en.md#orders-console-transport)

<a id="transport-example"></a>

#### Give large responses their own transport budget

Put the following in `config/_serv.yml` in an API service with initialized Crypto and a shared registry. This uses the `/backend/api` prefix and assumes the application exposes a JSON report export under it. Use the full path of your mounted export route. Probes continue using ordinary HTTPS requests.

```yaml schema=@h-ai/serv:ServConfigSchema
http:
  apiPrefix: /backend/api
transport:
  maxPlaintextBytes: auto
  maxFutureSkewSeconds: 60
  maxRequestAgeSeconds: 300
  routePlaintextBytes:
    /backend/api/reports/*/export: 8388608
  keyExchangePath: /backend/api/_hai/key-exchange
  excludePaths: [/health, /ready]
```

Set the client's `baseUrl` to the HTTPS origin followed by `/backend/api`, and its `transport.keyExchangePath` to `/backend/api/_hai/key-exchange`. Changing the API prefix leaves the default key exchange path at `/api/v1/_hai/key-exchange`. Confirm key exchange at `/backend/api/_hai/key-exchange`. Ordinary routes keep the 1 MiB limit. The export route can return more than 1 MiB and up to 8 MiB of UTF-8 plaintext. Test with data below and above the limit, and check the proxy can accommodate encrypted requests. [Client integration](../function/api-client.en.md#client-integration)

<a id="fullstack-key-exchange-example"></a>

#### Exchange keys through a Fullstack gateway

Put the following in the Fullstack backend's `config/_serv.yml`. Business requests use `/backend/api` and the key exchange uses `/exchange/keys`. Public probes still use their configured `http.health` paths.

```yaml schema=@h-ai/serv:ServConfigSchema
http:
  apiPrefix: /backend/api
transport:
  keyExchangePath: /exchange/keys
```

In a Docker SSH Provider deployment, the gateway forwards `/exchange/keys` unchanged to Serv. The public `runtime-config.js` supplies `apiBase` and `apiKeyExchangePath` to the Web client. Route both paths to the same backend when managing your own gateway. Open the gateway URL in a browser, verify `POST /exchange/keys` returns 200, and check that an encrypted business request reaches an endpoint under `/backend/api`. [Fullstack deployment](../function/deploy.en.md)

<a id="a2a"></a>

### A2A HTTP endpoints

| Field | Type and constraints | Default | Purpose |
| --- | --- | --- | --- |
| `a2a` | `false` or an object | `false` | Sets the public A2A discovery and message paths. The application also supplies the initialized handler. |
| `a2a.cardPath` | Site-absolute path | `/.well-known/agent-card.json` | GET route that returns the public Agent Card. |
| `a2a.rpcPath` | Site-absolute path distinct from `cardPath` | `/a2a` | POST route for authenticated JSON-RPC requests, including operations that return SSE. |

#### Let a partner’s program review the order backlog

Publish the orders assistant on a dedicated URL. Use the actual request paths and configure the reverse proxy to forward them to the host that mounts the handler.

```yaml schema=@h-ai/serv:ServConfigSchema
a2a:
  cardPath: /.well-known/agent-card.json
  rpcPath: /partners/orders/a2a
```

Set the Agent Card URL in `_ai.yml` to `https://api.orders.example.com/partners/orders/a2a` and declare `X-Agent-Key` as the header in `a2a.security.apiKey`. At startup, initialize AI and IAM, register the orders assistant executor, and mount the HTTP handler. Pass the issued partner key through `ORDERS_AGENT_KEY`. Serve both endpoints over HTTPS without application-layer transport encryption. [A2A](../function/ai.en.md#a2a)

```sh
orders_origin=https://api.orders.example.com
curl --fail-with-body -sS "$orders_origin/.well-known/agent-card.json"
curl --fail-with-body -sS "$orders_origin/partners/orders/a2a" \
  -H "X-Agent-Key: ${ORDERS_AGENT_KEY:?}" \
  -H 'Content-Type: application/json' \
  --data '{"jsonrpc":"2.0","id":"orders-backlog-1","method":"SendMessage","params":{"message":{"messageId":"orders-backlog-1","role":"ROLE_USER","parts":[{"text":"Summarize the order backlog."}]}}}'
```

Discovery returns the advertised JSON-RPC address. A successful call returns a JSON-RPC `result`. A missing or invalid key returns HTTP 401. For a subdirectory deployment, include the mount directory in both configured paths.

<a id="audio"></a>

### Live voice WebSocket

| Field | Type and constraints | Default | Purpose |
| --- | --- | --- | --- |
| `audio` | `false` or an object | `false` | Configures a live voice path for the Node host in `serv.listen()`. The app supplies voice operations, ticket verification, and business authorization. |
| `audio.path` | Site-absolute path | `${http.apiPrefix}/ai/audio` | WebSocket upgrade at the specified site path. An explicit path stays absolute even outside the business prefix. |

#### Transcribe a spoken note as the auditor dictates it

In an orders API with speech models and single-use tickets, mount the live voice endpoint at `/voice/orders`. Enable WebSocket forwarding at that path in the gateway.

```yaml schema=@h-ai/serv:ServConfigSchema
audio:
  path: /voice/orders
```

Sign in with a user who can edit audit notes. Obtain a single-use ticket and connect to `wss://api.orders.example.com/voice/orders`. The page sends microphone audio as the user speaks and displays the transcription as it arrives. Reusing the same ticket should fail. For one-off text-to-speech or recording transcription, use the HTTP endpoints. [Ticket and connection example](../function/serv.en.md#audio-ticket-example)

## Apply and verify

After restarting, check health, authentication, and API routes from the same domain users visit. Verify the trusted address reported by the proxy, browser preflight, and key exchange in turn. Update deployment configuration if you changed the public proxy routes or container probes. [Request access and client origins (Chinese)](request-access.md)
