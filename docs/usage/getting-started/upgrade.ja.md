# アプリのフレームワーク依存関係を更新する

[初回リリースの手順](workflow.ja.md) · [保守と検証](../governance/README.ja.md)

依存関係、公開 API の呼び出し、設定、Skills をまとめて移行します。アプリが使うすべてのパッケージについて、指定したレジストリに対象バージョンが公開されていることを確認してください。

<a id="compare-release"></a>

## 現行版と公開版を比べる

アプリのディレクトリで [hai-framework-sync](../../../packages/cli/templates/skills/hai-framework-sync/SKILL.md) を使い、インストール済みの版と移行先を比較します。この手順ではレジストリのタグ、実際のパッケージ、Node の要件、依存関係カタログ、ロックファイルを調べます。一部が未公開の場合やネットワークに接続できない場合は結果を記録します。移行方法を検討する段階では比較だけを実行できます。

<a id="migrate-app"></a>

## アプリ固有のルールを保ちながら移行する

業務要件を満たす公開 API が移行先にある場合は、その API を使います。呼び出し元を変更したあとで参照を調べ、不要になった実装や依存関係を整理します。アプリ固有のルールは残してください。パッチが必要な場合や設定仕様・業務フローが変わる場合は、実装前に変更案と復旧条件を確認します。

`hai init` で不足している AI 用の入口ファイルや Skills を補えます。既存の Skills は前のテンプレート、アプリでの変更、新しいテンプレートを比較してマージします。受け入れ済みの要件とタスクの記録も保管します。

<a id="data-compatibility"></a>

## データとセッションの互換性を確認する

データベース、セッションキャッシュ、オブジェクト、ボリューム、管理対象の認証情報をバックアップします。分離した環境でデータベースのコピーを使い、移行先の初期化、ログイン、永続データを確認します。現在の CLI でイメージを再ビルドし、[ロールバック](../configuration/delivery.md#失败恢复与发布后回滚) 時のデータ復旧はアプリの手順に従います。

<a id="verify-upgrade"></a>

## 更新後の成果物を検証する

型チェック、lint、ビルド、テストを実行し、認証、データ、画面、変更した操作は E2E でも確認します。対象のイメージとインストーラーを再作成してデプロイし、実際に動作するバージョンとユーザー操作を確認してください。
