# 用户反馈的操作与故障排查

[功能流程](../function/feedback.md#feedback-workflow) · [配置](../configuration/feedback.md) · [数据](../data/feedback.md)

## 用两个账号验证反馈

1. 用提交者账号在登录后的页面做几次操作，再打开「反馈问题」。检查截图、近期浏览器日志和操作回放。录制一段短视频，移除不需要的材料，勾选服务端日志并提交。在「我的反馈」确认状态为「待处理」，验证首帖只显示实际发送的材料。
2. 用具有 `feedback:read` 和 `feedback:process` 的账号打开处理列表。打开同一份反馈，发送一条「要求补充信息」的消息，附一份步骤文件。状态应为「待用户补充」。
3. 提交者刷新「我的反馈」，读取补充请求和步骤文件，回复一张截图。详情应显示新消息，状态回到「待处理」。
4. 处理人员刷新详情，预览用户截图、回复结果，然后标记「已处理」。提交者从同一份反馈读取结果并可继续回复。

## 定位提交、回复或附件问题

| 现象 | 检查方式 |
| --- | --- |
| 找不到反馈入口 | 确认应用挂载了反馈接口，并授予登录用户 `feedback:create`。提供处理列表的账号需要 `feedback:read`。 |
| 详情、回复或下载失败 | 核对账号、服务端确定的业务范围及反馈归属。处理其他人的反馈需要同时拥有读取和处理权限。附件 URL 用反馈 ID 和附件 ID 一起授权。 |
| 文件超限或提交失败 | 检查是否超过 5 个手动附件、单文件 5 MiB 或一次发送合计 10 MiB。首帖现场材料也占用合计容量。开启传输加密或反向代理时，核对反馈路由和上游请求大小。 |
| 首帖缺少近期日志或回放 | 浏览器重载会清空本地材料。服务端日志需要提交者勾选，并且日志所在实例、可信用户和业务范围与提交匹配。检查日志产生时间和宿主的请求上下文。 |
| 录屏不可用 | 使用支持屏幕共享的浏览器，并允许分享所选画面。截图或手动附件仍可随首帖发送。 |
| 请求结果因断网未知 | 用原提交或消息 UUID 重试。同 ID 已保存时取回该记录。 |
| 页面只报内部错误 | 收集请求路径、发生时间及主应答的追踪编号，在应用现有日志中查对应请求。 |

在新数据库中启动 RelDB 后，用配置的应用 ID 初始化 Feedback。首帖正文、保留的现场和手动附件在同一个关系库事务中保存。 [容量和权限](../function/feedback.md#feedback-limits)
