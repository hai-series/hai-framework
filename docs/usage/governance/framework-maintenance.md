# 维护框架与同步资料

[维护与验收](README.md) · [维护人员路线](../overview/reading-paths.md#框架维护人员修改一次所有使用入口同步)

公共变更需要同时回答三件事：哪些使用方式改变了，哪些调用方会受影响，哪些资料和测试需要同步。仓库实现以当前公开类型、消费点和真实运行结果为准。

## 先固定变更范围

读取[AGENTS](../../../AGENTS.md)及[工作规范](../../../.agents/instructions/workspace.md)，搜索实现、引用、测试、README、Skills和CLI模板，保留已有工作。按生命周期模块、工厂、函数、HTTP适配和组件判断契约，不套统一init/close。

先列问题的场景、影响、依据和建议，合并同根因。普通内部修复在已有授权范围内持续实施；只读审查按只读范围交付。

## 重要变更先让维护者作决定

新增、修改或删除功能涉及 `type`/interface/Schema 的结构或语义、配置/环境变量、核心流程、模块边界时，先按 [hai-change-plan](../../../.agents/skills/hai-change-plan/SKILL.md) 给出方案，再等待用户明确决定。已经确认且范围未扩大的方案继续执行；发现新的重要影响只确认新增部分。

方案先用简短语言说清楚：为什么改、改后如何使用、哪些模块/应用/模板与旧配置受影响、同步什么、如何验证和恢复。必要路径放在结论后作依据。比如“把文件下载放到网站的 files 目录下，会影响存储地址配置、签名和代理规则；一并修改并用真实下载与失败恢复验证”，比只列内部函数名更容易判断。

确认后同步相关 README、环境变量与模块配置说明、docs、GitHub Pages 的内容源/导航/图片、源码注释、公开类型说明、调用方、测试和 CLI 模板；无影响项注明原因。安装与最新版介绍引用 npm 注册表和动态徽标，通过 `pnpm view` 查询，不写死当前框架发布号。

## 同步实现和使用入口

1. Schema与实际消费点：字段类型、必填、默认、范围和覆盖规则一致。
2. 调用方与错误边界：先判断HaiResult，失败保留可恢复业务原因，内部诊断不直接公开。
3. 示例与模板：生成项目能安装、编译、运行，环境和原生条件准确；项目私有路径不复制到模板。
4. 文档与Skills：配置手册集中解释参数，操作指南展示流程，README/LLMS负责导航，Skills负责执行路径与边界。
5. 测试与截图：保留独有风险覆盖，修复旧断言时不丢权限/异常/恢复；界面和结果变化重拍当前图。

文档正文人工维护，脚本只检查字段、引用和例子，不从Schema拼成说明。官网直接消费这些Markdown和`navigation.json`，不另存一套内容。

## 按影响验证

先typecheck、lint、适用build，再test和相关E2E。普通失败先汇总根因再修复，依赖真实前置失败不得拿旧产物冒充通过。AI资料改动执行check:`skills`/引用检查，模板执行scaffold门禁。

完整验收按用户要求执行；日常局部修改按影响选范围，避免为可逆低影响文案写镜像测试。发布后查询实际GitHub Actions和npm，而非只看本地版本。

## 交付说明

先说解决了什么和使用变化，再给必要位置、测试和未验证边界。对每项区分已确认、待验证、计划修改、已完成和未解决。报告敏感信息已清理，运行产物与正式使用截图分别保存；纯文档改动说明没有运行时代码影响。
