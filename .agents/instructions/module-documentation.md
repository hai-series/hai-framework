# 框架模块文档规范

用于 hai-framework 的模块 README、配置页、数据页、功能页和公开源码注释。新写、改写和审查都按这套规范执行。

## 开始前核对什么

先确定读者要完成的操作，例如「用户申请验证码，服务端把验证码发到他的手机」。沿实际调用核对公开入口、配置从哪里读取、字段在哪里生效、数据怎么保存和清理、调用方如何判断结果。事实来自对应版本的公开类型、配置消费代码、表定义或迁移、缓存读写、调用方和测试。

按任务范围逐个检查模块、页面和语言。先看完章节和示例，找出会妨碍读者完成操作的遗漏或错误。脚本可核对字段、链接和章节顺序。正文要根据真实行为编写，并逐页通读。

使用手册说明当前的配置契约、操作步骤和可观察结果。版本迁移、旧字段清理和发布变化放在对应的升级说明或变更记录中。检查既有数据时，从当前约束和读者要完成的检查、修复或导入任务出发。

## 各页面怎么写

### README

`packages/<模块名>/README.md` 开头说明模块用途、主要能力和运行环境。中英日版本使用以下六个二级标题，按表中顺序排列。

| 中文 | English | 日本語 | 内容 |
| --- | --- | --- | --- |
| 快速开始 | Quick Start | クイックスタート | 实际安装方式和同语言的最小接入链接 `#quick-start`。 |
| 配置清单 | Configuration Reference | 設定一覧 | 配置入口和配置页链接。 |
| 功能说明 | Features | 機能 | 按职责概览公开能力，链接功能页和重要入口。 |
| 数据结构 | Data Structures | データ構造 | 说明由谁保存数据，链接数据页。 |
| 开发测试 | Development and Testing | 開発とテスト | 可执行的构建、检查和测试命令及其前提。 |
| 许可证 | License | ライセンス | 许可证声明或链接。 |

具体字段、完整示例和操作流程放在对应参考页。跨模块指南按业务任务串联这些参考页。

### 模块参考页标题

配置、功能和数据参考页的一级标题使用模块 `package.json` 的公开包名、一个空格和对应的本地化页名。例如 `@h-ai/reldb 配置`。跨模块指南按读者任务命名。

| 参考页 | 中文 | English | 日本語 |
| --- | --- | --- | --- |
| `configuration` | 配置 | Configuration | 設定 |
| `function` | 功能说明 | API Reference | API リファレンス |
| `data` | 数据结构 | Data Structures | データ構造 |

修改已有标题时保留页面路径、章节锚点和旧标题的跳转目标。若新标题会生成不同的 ID，在页首保留旧 ID 的显式锚点。

### 配置页

`docs/usage/configuration/<模块名>.md` 说明应用实际读取的配置文件和环境变量。

1. **配置入口**。说明文件位置、谁读取、覆盖顺序、改动后何时生效。共享字段归入实际消费它的文件和路径。没有独立文件时，说明设置归谁读取，并链接配置或调用入口。
2. **配置清单**。按实际作用分组。每项给出完整路径、类型或可选值、必填条件、默认值和用途。有范围、单位或组合约束时一起说明。枚举项写全，示例中的自定义名称和框架固定取值分别标明。函数、工厂和组件的调用参数归功能页，响应结构归数据页。
3. **配置示例**。先给清单再给示例，或把示例放在对应分组的字段之后。每个示例说明为哪个业务准备、配置放哪里、修改哪些值以及生效后如何确认。影响接入方式或业务结果的配置应有可照做的例子。展示框架默认值和模板选用值时标明来源。

### 数据页

`docs/usage/data/<模块名>.md` 先用实际记录说明为什么保存、谁会读写，然后给出可查询的存储清单。

1. **数据库**。先用 Markdown 总览表列出表数、表名和用途。条件创建的表写清条件，每张表仅列一次。再为每张表提供一张字段表，逐列写名称、类型、可空性、默认值、用途和示例。主外键、唯一约束、索引和清理条件就近说明。区分数据库默认值和应用首次写入的值。
2. **缓存**。先用 Markdown 总览表列出键或键族的数量和用途。每类单列字段表，写完整键模板和变量来源，以及值的字段、类型、默认值和示例。说明有效期、续期、删除条件及共享范围。计数和配额写清统计对象、周期如何开始及重置、满额时会发生什么。
3. **文件和运行时数据**。按实际结构说明所有者、读写方式和保留时间。没有模块自有存储时，说明谁负责保存和从哪个入口读取。

表、缓存值、文件记录和主要接口响应各给一个能解释其用途的示例。标明哪些字段是节选或已脱敏，解释关联编号、状态和时间单位。示例按共同数据契约展示，只有后端差异影响取值、约束、容量、读写、迁移或清理时，才在对应字段或场景说明。

### 功能页

`docs/usage/function/<模块名>.md` 先在 `#quick-start` 给出最小可运行的接入流程。`#api-reference` 下按读者任务组织全部公开能力。每个大功能用三级标题标明任务和真实入口，下面按「用途 → 接口清单与字段说明 → 场景」展开。CLI、组件、工厂实例和普通函数使用各自真实的入口及生命周期。

#### 接口清单

中文用四级标题「接口清单」，英日用「Interface list」「インターフェース一覧」。表头统一为 `API | 用途 | 参数与默认值 | 返回值或失败 | 调用示例`，英日翻译列名并保持列顺序。

- API 列按参数顺序写实际调用签名，如 `storage.file.put(key, data, options?)`，用 `?` 和 `...` 标出可选和剩余参数。属性保留名称，组件写实际标签和 props，CLI 写实际命令、参数和选项。
- 参数列说明每个输入会读取、选择或改变什么，并写类型、默认值和生效条件。省略和留空得到不同结果时分别说明；编号、回执和更新版本写清由谁生成、从哪一步取得。枚举值、嵌套字段和其他补充解释紧跟清单，字段多时用清单下的五级标题和独立字段表。共用字段可链接同语言的字段表。完整场景从这些说明之后开始。

#### 场景示例

一条场景对应一个实际任务，用四级标题「场景：……」，英日用「Scenario: …」「利用例：……」。按「业务触发 → 必要准备 → 代码 → 结果与下一步」写。同一场景可串联多个接口，清单中每项都应有实际用法和可观察结果。

- 准备写清调用方、环境、依赖和输入的来源。场景用到配置时，链接到对应的配置示例。配置里的渠道名、模板名、变量和调用值应一致。说明变量从哪里传入、填到哪里、替换后得到什么。只有演示校验时才以单独调用 Schema 作为示例。
- 每次公共业务 API 调用都在代码块里就近说明实际参数、结果和有影响的失败或分支。重复调用同样解释本次目的。返回 `HaiResult` 时直接检查 `success`，交代 `data`、`error`、`null` 或无业务数据在这一步的含义。事务、启动与框架控制流按各自的失败契约写。
- 用实际行为解释字段和术语。读者看到「排队」时，应知道哪条记录已保存、如何查、何时发送。看到「回执」时，应知道谁给出哪个编号、能确认到哪一步。重要分支用同一组业务输入演示，例如让白天与夜间的同一通知得到不同结果。外部服务、时间或随机值按可复现的示例条件说明。
- 工厂示例演示返回实例的使用与释放。组件示例展示操作、事件或绑定值及页面结果。流式或多方协作示例交代各方用哪些共享资源、如何传递标识、各自何时观察到结果以及谁负责清理。模拟多个参与者时说明模拟范围。
- 多阶段、异步状态、取消重试或跨端协作容易误读时，在该场景旁放流程图、时序图、状态图或数据流图。图前写明模式和前提，图后用示例走一条具体路径。核对执行者、分支、状态和清理，区分受理、持久化和最终完成。图使用网站支持的格式并保留图源，三语同步，提供替代文本和尺寸，桌面与窄屏均可读。

### 源码注释

公开声明用中文 JSDoc 说明用途、输入、默认值、结果和失败。示例走真实公开入口，并按功能页的规则解释调用。内部注释说明关键分支、并发、权限和清理的依据。验证命令见 [JSDoc 与示例验证](module-conventions.md#jsdoc-与示例验证)。

## 三语与链接

- GitHub Pages 直接使用 [使用手册](../../docs/usage/README.md) 和 [导航](../../docs/usage/navigation.json)。新增或移动章节时核对索引、上下文链接及已有中文入口。
- 英日使用 `.en.md` 和 `.ja.md`，优先链接同语言页面。对外链接和换语言需要定位的同一章节共用显式锚点，如 `<a id="quick-start"></a>`。同页包括自动生成的标题 ID 在内保持唯一，旧锚点随实际内容保留。
- 三语核对章节、接口、示例、图和结果的一致性。有缺译时保留 `<!-- translation: partial -->`，明确缺译范围并链接中文章节。整页未译使用已有的中文回退。

## 交付前核对

1. **结构和事实**。逐页对照「各页面怎么写」，核对清单覆盖、章节顺序、实际入口和字段。逐个走一遍场景，确认读者能从配置找到正确的调用，并从结果判断下一步。新增说明放回对应章节，合并重复内容。
2. **示例和门禁**。有公开 Schema 的完整配置示例，在 YAML 或 JSON 围栏标记 `schema=@h-ai/<包>:<Schema>`，执行 `pnpm check:usage-examples`。从实际公开入口检查关键代码示例的类型，并运行能区分所写结果的正常、失败或边界路径。运行受影响的检查，README 用 `pnpm check:readme`，skills 和规则用 `pnpm check:skills`。记录样例数据、替身和真实服务各自验证了什么。
3. **网站和交付**。导航、标题、链接、语言或搜索受影响时，执行 `pnpm --filter framework-website compile`。在部署挂载路径核对旧链接、同章换语言、侧栏、搜索、缺译提示和桌面／窄屏呈现，可复用 [官网文档用例](../../apps/framework-website/e2e/website.spec.ts)。需要线上验收时，先确认对应提交已经发布，再检查线上页面。按 [工作规范](workspace.md#验证与交付) 报告已执行门禁、未验证原因、剩余缺译和运行时代码影响。
