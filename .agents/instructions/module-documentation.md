# 框架模块文档规范

适用于框架包 README、`docs/usage` 中的使用手册和模块源码注释。写作与审查共用以下要求。应用和生成模板仍按各自规范维护，公共契约变动时按影响同步。

## 先核对事实与覆盖范围

从读者实际要完成的操作出发，先读现有目录和完整的使用路径，再核对 `package.json.exports`、实际公开类型、配置读取和消费点、表定义或迁移、缓存读写、调用方与测试。发布包用法以对应版本为准。生成或审查一个模块时，逐项对照这些来源梳理配置、数据结构和公开功能，找出缺失、错误、重复和不好理解的内容。不要只改用户举出的几句话，也不要机械改写无关模块。

## README 与参考页

每个模块的中、英、日 README 开头用几句话介绍用途、主要能力和运行环境。六个二级章节统一按以下顺序排列：

| 中文 | 英文 | 日文 | 本节写什么 |
| --- | --- | --- | --- |
| 快速开始 | Quick Start | クイックスタート | 给出真实的安装方式，链接同语言功能页的最小接入示例（`#quick-start`）；只保留开始使用所需的信息。 |
| 配置清单 | Configuration Reference | 設定一覧 | 简述配置入口，链接 `docs/usage/configuration/<模块名>.md`。 |
| 功能说明 | Features | 機能 | 按职责概览能力，链接 `docs/usage/function/<模块名>.md` 及关键功能锚点。 |
| 数据结构 | Data Structures | データ構造 | 简述数据由谁保存，链接 `docs/usage/data/<模块名>.md`。 |
| 开发测试 | Development and Testing | 開発とテスト | 给出真实存在的构建、检查和测试命令，说明必要前提。 |
| 许可证 | License | ライセンス | 只保留许可证声明或链接，作为最后一节。 |

详细说明只维护在对应参考页。补充内容并入已有章节；README 不重复完整配置、数据库字段、缓存 key、API 表或长示例。概览的同级项目按职责归纳，粒度相近。跨模块操作指南按用户任务写步骤，字段、签名和其他细节链接到相应模块页。

- **配置参考**：`docs/usage/configuration/<模块名>.md` 只收录真实配置文件中的字段，例如 `config/_<名称>.yml`、`hai.json`、`capacitor.config.ts` 和实际消费的环境文件。先核对文件、Schema、读取者及消费点，再写用途、类型、必填条件、默认值、取值范围、单位、加载/重启时机和覆盖顺序。函数或工厂的 `config/options`、初始化依赖对象、回调、客户端实例参数和 UI props 属于功能参考；接口返回的公开配置结构属于数据参考，不能仅因名称含 config 或存在 Schema 就放进配置页。没有独立配置文件的模块只说明这一事实并链接功能参考，不臆造 `_crypto.yml` 等文件，也不把代码参数表换个标题保留。共享 Schema 在其他模块文件中被消费时，使用实际文件和完整字段路径，不能列成本模块的顶层文件配置。框架默认、模板选择、示例值分别说明。
- **数据参考**：逐张说明表的用途、所有者、字段含义、类型、是否允许空值、默认值、主外键、唯一约束和相关索引。逐类记录缓存 key 的完整模板、每个变量的含义、值结构、默认 TTL、续期和清理条件以及读写方。模块没有自有数据库或缓存时，说明数据实际存在哪里、由谁管理；不要虚构结构。如果数据落在文件或其他持久化后端，也说明结构和保留方式。每张表、每类缓存值、文件记录及主要接口/运行时结构都须给出与当前实现一致的示例数据，不能只有字段表或调用代码。示例标明对应表、键或类型、时间和单位，以及 JSON 列的物理表示与业务对象的区别；仅展示部分字段时明确写“字段投影”，不能冒充可直接写入的完整记录。关联示例使用一致的标识，说明空值、状态与过期关系。使用虚构业务内容，令牌、私钥和个人信息脱敏，脱敏占位不得声称可用于真实认证。三语同步结构、示例及解释。 先用日常语言解释每张表、每类记录为什么存在：谁在什么场景写入、谁靠它做决定、何时更新或删除，以及丢失或过早删除会造成什么。不要把字段名、CAS、TTL、nonce 等实现词直接当作用途；先说“记住已经用过的请求编号，避免重复执行”，再按需解释技术做法。每份示例单独说明它表示哪个业务状态、关键值各是什么意思、与关联记录怎样对应；不能只堆一个大 JSON、附一句“字段投影”就算说明。计数和配额必须讲清统计对象、共享范围、周期起止、满额结果、恢复时机，以及它和累计总量、有效期、业务限流的区别。

## 功能清单与场景示例

1. 功能页用 `#quick-start` 给出最小使用流程，在 `#api-reference` 下按职责覆盖全部公开功能。多个子功能分别使用三级标题，标题先说读者要做什么，再标真实入口，例如 `### 文件与环境配置：\`core.config\``、`### 记录日志：\`core.logger\``。生命周期、CLI 命令、组件族和工厂返回实例按实际职责分组，不臆造模块接口。单一功能也保留同样的清单与场景顺序。
2. **每个大功能先说明用途，再有 `#### 接口清单`，之后才是 `#### 场景：……`。** 英日对应标题使用 `#### Interface list` / `#### インターフェース一覧` 和相应场景标题。清单统一五列：`API | 用途 | 参数与默认值 | 返回值或失败 | 调用示例`，英日翻译列名并保持顺序。输入须说明业务含义、必填项和默认值，不能只写“未知值”或照抄 `unknown`；示例变量在本节有明确来源。不要每行重复添加“场景”链接，不能把全部 API 堆在页首，也不能用仅有类型或调用片段的总表代替场景。

   `API` 列写可调用入口及其参数顺序，例如 `storage.file.put(key, data, options?)`。`?` 标出可省略的参数，`...` 标出剩余参数，无参调用写 `()`。属性和 Schema 常量保留名称，组件登记实际的标签和 Props，CLI 使用命令行的形参和选项写法。三语表中的签名一致，参数名称与下一列对应。

   「参数与默认值」列按签名顺序写明每个参数的类型和作用，说明必填条件、省略后的行为和有效取值。说明参数会读取、选择或改变什么，例如 `limit` 限制本页最多返回多少条；只列 `limit?: number` 不够。对象参数先在接口行说明用途，多字段、嵌套或按模式生效的 `options`、`input` 在本节用独立字段表展开，或链接到同语言的共用字段表。字段表列出字段及类型、必填或默认值和生效条件。正则、回调、条件必填项及会改变结果的选项组合附可复制的示例，写明实际输入及对应的返回数据、错误或可观察变化。

3. 场景按实际操作顺序串联相关接口，例如加载→校验→读取→监听→清理；不要求每个接口写一个孤立小节。逐项核对清单中的每个接口都有调用示例及输入输出说明，属性说明读取条件和值，CLI 说明参数与可观察产物，组件说明 props、用户操作、事件/绑定值和页面结果。返回实例的工厂同时演示实例如何使用与释放。仅在表格里写一个方法名、返回类型或“见示例”不算覆盖。
4. 场景讲清**谁在什么条件下调用、输入从哪里来、调用后能看到什么**。先给前提与具体输入，再给代码及对应输出或可观察效果，最后说明有实际影响的限制、失败和清理。变量应完整；依赖、配置、平台和应用提供的函数须明示。返回 `HaiResult` 时先判断 `success`，分别解释成功数据、失败错误与成功无数据；抛错、流和普通返回值按真实契约处理。随机值、时间、外部服务和平台相关结果标明前提与示例性质，不能编造固定响应。关系紧密的方法可共用示例，但不能漏掉其中任一接口的结果。

   **在代码块内按调用逐次说明。** 每次公共业务 API 调用都在调用行或紧接在它前面的注释中说明实际传入的值及来源、成功数据或可观察变化，以及影响本步的失败或分支。同一 API 重复调用时，分别说明每一次的作用和结果。布尔值、`null`、数组要说清本步的业务含义。无业务返回值时写出状态、事件或产物变化。基础语法与标准库用法仅在影响示例结果时解释。把代码块单独复制出来，仍应能读懂每次调用的输入、结果和相关分支。块外段落和接口清单可补充背景，逐次注释放在示例代码内。对不支持注释的格式，紧邻代码块按步骤说明。

   示例直接检查 `HaiResult.success` 并处理失败，不引入 `value`、`unwrap` 等拆包辅助函数，也不靠辅助函数把业务失败改成抛异常。事务回滚、宿主启动失败或要求抛错的回调按真实控制流展示，并说明为何要中断，不能改成返回值而改变提交或执行结果。密码记录、密文编码与算法参数须解释每个字段的实际含义，并与代码中显式选项保持一致。异步事件须区分“生成/受理完成”和“播放/执行/持久化完成”，不能把前者写成已经产生后者的效果。
5. 重组时将参数、约束和专题说明归回所属大功能，统一 `core.md` 与其他模块的层级、表头、示例和结果写法。二级标题组织整页，三级标题划分大功能，四级标题列清单和场景；只有确属某场景内部的子步骤才用五级标题。不为迁就脚本把原章节一律降级，也不把所有标题改成加粗行。以当前源码核实功能覆盖，逐文件通读章节树、场景顺序与示例，三语逐节对应；自动化只辅助结构调整与验证，不从 API/Schema 自动拼凑正文，也不能用批处理成功替代人工审查。

## 复杂接口与辅助图

功能页中的接口若包含多个阶段、条件分支、异步状态、跨端/跨节点协作，或取消、续期、重试和清理行为，应在对应场景配图。先逐模块识别读者容易误解的机制；单步读写、简单纯函数不必为了数量配图。图辅助正文与真实调用示例，不能替代接口清单或输入输出说明。

| 读者需要弄清什么 | 适合的图 |
| --- | --- |
| 先做什么，哪个条件决定继续或失败，如握手、登录、事务提交 | 流程图；标出关键判断、成功/失败出口和可选步骤 |
| 浏览器、服务端、存储各自在何时做什么，如请求加密、上传、回调 | 时序图或按执行者标注的流程图；区分发送、受理和完成 |
| 对象何时可用、取消后是否停止、结果未知时怎么处理 | 状态图；写清触发转换的操作、终态和恢复条件 |
| 密钥、令牌、配置或任务由谁保存，哪些共享、哪些只在本地 | 职责/数据流图；说明所有者、流向、保存与清理边界 |

- 图放在实际讲解它的场景旁，沿用章节层级，不在页首堆图或另建脱离流程的“图集”。图前说明它覆盖的入口、模式和前提；图后用日常语言走一条具体路径，解释关键分支、输出或可观察效果。不能只放图片再写一句“见图”。
- 对照当前实现、公开契约和调用方逐项核对执行者、顺序、状态、箭头及边界。可选配置不能画成默认必经步骤；借用资源与自有资源、进程内状态与共享状态分开说明。取消、关闭或失败之后的状态与资源释放也要核对。
- 多客户端、进程或服务协作的示例，应标明各步骤由谁执行、各方使用的共享资源或命名空间、必要标识或凭据的来源和传递方式，以及每方实际观察到的结果。单进程模拟须写明模拟范围。若场景承诺多个独立参与者协作，按实际隔离边界演示和验证，并说明启动顺序与清理责任。
- 清楚区分“已受理、生成完成、已持久化、外部执行完成”。认证/验签通过不代表业务授权或订单提交；事务和租约不撤销已发生的外部效果；重试、接手和恢复必须符合实际幂等条件。图中的简化不得改变这些含义，专题图应明示没有展开的路径。
- 优先采用可维护的 Mermaid、SVG 等格式，并确认文档实际渲染端支持。只显示 Mermaid 源码的页面应沿用既有静态 SVG/图片方式，无需为配图修改产品运行逻辑。图片提供准确的替代文本、固定尺寸和可维护图源；区分状态不能只靠颜色，检查文字、箭头与标签不截断或重叠，窄屏可阅读或打开原图。
- 中英日版本同步图、位置、条件和解释，图内文字使用页面语言，已有缺译标记如实保留。修改相关行为或文档时同时更新图；验收既检查图片引用和尺寸，也实际查看构建后的桌面及窄屏页面，不能只以图源可解析或批量生成成功交付。

## 用读者能判断的行为解释术语

用具体的执行者、配置位置、字段和可观察结果写正文。首次引入术语时解释它在本场景意味着什么；必要时再带出类型或 Schema，并说明它校验哪份输入。配置示例从模块真实的初始化或配置入口使用，独立的 Schema 调用只在演示验证本身时使用。脚本可帮助核对字段、公开方法和示例，正文在理解实际行为后编写。遇到容易误解的机制，用只改变一项输入的对照例子解释差别。例如：

| 容易误解的点 | 应交代的行为 |
| --- | --- |
| 工厂返回的“占位”对象 | 用订单查询演示模块未就绪返回失败、初始化后查到数据或成功返回 `null`、关闭后再次失败；说明是谁切换到真实实现。 |
| “解析可信客户端地址” | 对比直接连接和经代理连接，说明套接字地址和代理报告的地址各来自哪里、哪一个用于访问策略；区分信任谁报告来源与允许谁访问。 |
| 默认值、合并或集合运算 | 给出输入、输出和必要的类型；例如对照省略与空对象、父子 Logger 附带的字段，或交换差集参数后的结果。 |

这些是写法示例，按模块实际需要选择。不要保留聊天答复、“补充说明”等孤立章节；将新增信息并回相应功能，删除重复内容。流程图或截图要与真实行为一致，核对读取者、箭头顺序、优先级和结果；不能用画错的图替代说明。[使用文档与证据](../../packages/cli/templates/skills/hai-app-create/collaboration.md#使用文档与证据)中的通用约定同样适用。

源码注释与文档一起审查。公开声明的中文 JSDoc 说明用途、参数、默认值、返回和失败条件，示例从真实入口调用并按上文逐次说明公共业务调用。关键分支、并发、权限、状态和清理逻辑说明为什么这样做以及边界在哪里，避免复述代码或保留过期注释。详细要求与验证命令见 [JSDoc 与示例验证](module-conventions.md#jsdoc-与示例验证)。

## GitHub Pages 与三语维护

- GitHub Pages 直接使用 [`docs/usage`](../../docs/usage/README.md) 和 [`navigation.json`](../../docs/usage/navigation.json)，不另写一套正文。新增或移动章节时检查导航、对应索引与上下文链接。阅读顺序先让读者完成最小接入，再查配置、功能和数据，最后按需进入专题、运维或维护说明；各页面只承担自己的职责。
- 保留原中文 URL。英文用 `.en.md`（`/docs/en/…`），日文用 `.ja.md`（`/docs/ja/…`）；除语言前缀外，三语页面的路径一致。对应章节使用相同的显式锚点，如 `<a id="config-api"></a>`。锚点放在实际目标章节旁，同页 ID 唯一（含标题自动生成的 ID）；跨文件引用写明文件路径和片段。不同页面可使用同名 ID，不要求全站唯一。标题翻译或改名时核对已有引用，必要的旧锚点留在对应目标处；不要批量生成别名堆在页首，也不要给每个小节无条件添加锚点。README 和正文优先链接同语言页面。
- 三语应覆盖相同的功能、条件和示例结果。有未译章节的页面保留实际译文，并加 `<!-- translation: partial -->`；标明尚未翻译的范围，链接中文对应章节。整页未译时使用网站已有的中文回退和缺译提示，避免空白的译文占位。译文覆盖齐全后才移除标记，交付时如实报告剩余缺译。

## 验证与交付

- 核对新增和改动的链接、锚点、章节位置和语言归属。README 执行 `pnpm check:readme`；skills、规则和 AI 入口改动执行 `pnpm check:skills`。静态检查不替代通读或事实核对。
- 完整配置示例有对应公开 Schema 时，在 `yaml` 或 `json` 围栏加上 `schema=@h-ai/<包>:<Schema>`，运行 `pnpm check:usage-examples`。单独阅读每个示例代码块，沿调用顺序核对行旁注释是否说明了实参、结果和相关分支。关键代码示例从实际公开入口进行类型检查，并运行能区分所声明结果的正常、失败或边界场景。JSDoc 按模块约定校验。源码、图、文案和运行结果须一致，类型与 Schema 校验通过不能替代行为验证。
- 涉及网站导航、标题、链接、语言或搜索时，构建静态站点（`pnpm --filter framework-website compile`），用浏览器在部署时的挂载路径下验收：旧中文链接和锚点可访问；切换英日语言保持在同一对应章节；侧栏与搜索结果跟随所选语言；缺译提示和中文原文链接有效。可复用[官网的文档语言切换用例](../../apps/framework-website/e2e/website.spec.ts)。要求线上验收时，先确认对应提交的 CI 和 Pages 发布成功，再在部署站点复查。
- 按[工作规范](workspace.md#验证与交付)选择受影响范围，报告实际检查与缺译、未验证原因；纯文档修改说明对运行时代码没有影响。
