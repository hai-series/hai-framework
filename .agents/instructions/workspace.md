# hai-framework 工作规范

通用入口见 [AGENTS.md](../../AGENTS.md)。本文件供所有 AI 助手复用；模块、应用、测试的专属规则按入口路由读取，不默认加载全部 skills。

## 工作范围与决策

- 修改前搜索现有实现、引用、测试与文档，保留用户已有改动。优先删除本次范围内的冗余、复用现有能力，再考虑新增。
- 新增文件、抽象、配置或公共 API 前，确认真实调用点、现有扩展点、更简方案，以及是否泄漏内部细节。按任务复杂度简述结论，无须逐次输出固定问卷。
- 跨包改动先列影响范围和验证计划。能从代码确认的疑问先检索；只有影响目标、授权或不可逆操作且无法推断的信息才向用户澄清。
- 新增、修改、删除框架功能，涉及结构、配置/环境变量、核心流程或模块边界时，先按 [hai-change-plan](../skills/hai-change-plan/SKILL.md) 提交简明方案和实际影响，等待用户明确决定后再实施。一般修复授权不代替未说明的重要方案；已有具体确认且影响未扩大时继续，新增重要影响仅重新确认增量。普通内部修复不改变这些边界时按已有授权推进。
- 只读审查交付有证据的问题清单；用户要求修复时再实施。发现严重问题应及时说明，不以严重性替代修改授权。
- 不假定特定 AI 工具、记忆目录或外部服务存在。历史记录仅作线索，以当前源码核验；记忆写入遵循当前会话的授权和工具规则。

## 公共契约

- 先区分生命周期模块、纯函数/工厂、客户端与框架适配器。不能给所有包套用 `init/close` 或 `HaiResult`；具体边界见 [模块规范](module-conventions.md)。
- 有生命周期的模块按依赖顺序初始化，逐步检查结果，失败不继续启动；关闭时反序释放，覆盖并发初始化及失败清理。
- 返回 `HaiResult` 的操作用 `if (!result.success) return result` 处理业务失败；不以 `try/catch` 代替结果判断。SDK 异常、流迭代、显式抛错 API 按各自契约处理。
- 从包公开入口导入；已发布的 `/client`、`/adapter` 等子路径以 `package.json.exports` 为准，禁止导入另一个包的内部源码。
- 只导出真实消费者需要的类型/API；复用上游真实类型，不写本地仿造类型或纯转发适配层。
- 公共 API、类型、配置、错误码、模板变更后，全局核对 `packages/*`、`apps/*`、CLI 模板、README、skills、LLMS.txt、注释及测试，成套更新受影响部分。

## 实现约束

- 禁止 `any`、无说明的 `as unknown as T`、`console.log`、硬编码密钥；第三方类型缺失的必要断言必须注明原因。
- 代码注释中文，结构化日志消息英文；URL、配置和错误上下文先脱敏。用户可见文本走 i18n，同步现有全部 locale，包括 `zh-CN`、`en-US`、`ja-JP`。
- UI 负责显示与交互，业务逻辑放服务层；复用现有 `@h-ai/ui` 组件，避免复制内部翻译。不要手改 Paraglide 生成文件。
- 新 Provider/Strategy/Base 等抽象须有多个真实实现或调用需求；不要为未来假设增加兼容层、配置项、目录或转发链。
- 独立操作优先批量或有界并发；有依赖、顺序要求、事务或限流约束时保留串行。不能将所有循环中的 `await` 判为 N+1。
- 大数据按需分页/流式处理；热路径避免同步 I/O 和反复创建连接。定时器、监听器、连接及客户端在关闭和失败路径清理。
- 跨节点共享业务状态使用 DB/共享 cache；单机 memory provider、连接池及不可变配置可驻留进程内。可重试写入需明确幂等性。生产后端、22 包状态所有者、CAS/租约与故障恢复边界见[共享状态能力表](distributed-state.md)；不得以接入数据库或获得锁代替最终提交约束与外部效果核对。
- SQL 动态值用参数；动态标识符和 SQL 片段仅来自白名单/可信代码。不能用参数占位符替代表名、列名或排序方向。
- 边界输入做 schema 校验，复用 IAM 当前授权与框架守卫，再以资源 ID 查验所有者/租户/操作范围；需要时核验用途绑定的操作凭据。存储冲突、checksum 不匹配和通知失败/延迟不能静默转成成功。文件路径防逃逸；不渲染未消毒 HTML，不把不可信脚本当安全沙箱执行。
- 浏览器认证沿用项目已实现的 Cookie/内存 access token 流程；移动端使用安全 TokenStorage，禁止敏感 token 写入 localStorage。`PUBLIC_`/`VITE_` 变量不得包含密钥。

## 文档与 skills

开发、审查、测试与排错统一遵循[沟通与同步维护](../../packages/cli/templates/skills/hai-app-create/collaboration.md)：先给结论，围绕问题、触发场景、影响和改法说明，区分已确认、待验证、计划、完成与未解决。每批按实际影响核对使用文档、配置示例、截图、测试、CLI 模板和调用方；共享正文随模板一起交付，不在各 skill 重复维护。

- README 修改前先读取目录和目标章节，把新增内容合并到现有对应章节；没有合适章节时，在开发测试与许可证之前新增职责明确的章节。禁止把功能说明、升级说明、验收记录或使用示例直接追加到文件底部。
- “许可证 / License / ライセンス”只能出现一次，必须是最后一节，正文只保留许可证声明或链接。不得在其后添加标题或无标题功能段落；删除重复章节，代码示例中的标题不计入正文结构。功能说明放在“二次开发 / 开发测试 / Development / 開発とテスト”之前，不能只机械移动到许可证上方。
- 同一 README 有中英日版本时同步内容与章节位置；模板 README 一并核对。交付前通读修改后的章节顺序，运行 `pnpm check:readme`，不能仅依靠文本替换完成编辑。

- README 面向使用者，保留用途、最小可用示例、配置、错误、测试；仅对有生命周期的模块要求 init → use → close。
- 工作区开发 skill 位于 `.agents/skills/`；面向生成应用的模板位于 `packages/cli/templates/skills/`，复制到应用 `.agents/skills/`。两者面向不同读者，公共契约必须同步，不要求全文相同。
- `SKILL.md` 保留 `name`、准确且简短的 `description`、能力边界与任务路径；长 API 表和模式示例按需放在相邻参考文件，通过明确链接发现。
- 不复制通用常识、整段入口规则或同义关键词列表。缩短内容不能删掉初始化依赖、失败处理、环境边界、权限条件或必要示例。
- 示例若省略业务变量或上下文要说明；不能把依赖注入、默认值、返回类型、错误码写成猜测。技术 API 以对应版本源码/公开类型核验；应用业务以用户当前明确需求及其指定文档为准，模板代码和默认规则不是业务限制。修正文档时保留证据。
- 使用指南先理解用户任务、配置消费点和实际操作，再人工编写说明，不把 Schema、API 清单或测试汇总直接生成成正文。按步骤解释配置前后的变化，补当前运行截图。公开配置变化同步 `docs/usage`；可用 `pnpm check:usage-examples` 检查示例，但校验脚本不负责生成文案，也不替代运行验证。

## 验证与交付

测试临时工程、镜像、容器、辅助进程和数据须在 finally/teardown 自动清理，成功、失败和取消均执行；只清理本次创建的资源。日志、截图与报告保留到分析和交付结束再清理，不提交验收产物。

验证前先分析 Git 差异、行为、直接调用方和受影响用户流程，简述 test/E2E 选择依据。默认仅验证变更相关项，使用 workspace、测试文件或用例过滤；跨包契约和根配置只扩展到实际受影响的消费者，不自动提升全仓命令。影响不明先补分析，只有用户明确要求全量验收时才执行全仓验证。Windows PowerShell 使用 `pnpm.cmd`。

执行多项门禁必须先读 [分轮验证与集中修复](../../packages/cli/templates/skills/hai-app-tests/validation.md)。先在所选相关范围内收集可执行结果，再归并根因、集中修复；先定向确认失败和直接受影响项，不因局部修复从头重跑。下列顺序应用于已选范围，未要求全量时给命令添加 workspace/文件过滤，不是默认执行全部根命令或遇错即停的链条：

1. `pnpm typecheck`
2. `pnpm lint`（根命令包含 `pnpm check:skills`）
3. `pnpm build`（涉及构建、模板、发布或跨包契约）
4. `pnpm test`
5. `pnpm --filter <workspace> test:e2e` 或根 `pnpm e2e`（UI、路由、端到端流程）；CLI 模板交付用 `pnpm --filter @h-ai/cli test:scaffold-gates`。

收集阶段使用一次脚本化调度，逐项保存退出码、耗时与日志，只读取汇总和必要失败片段。本仓库另须注意：

- 根 `lint`、`build`、`test` 内含 `check:skills`、lint 或 `test:scripts` 等 `&&` 前置；前置失败不代表后面的 Turbo 任务已执行。需要继续收集时分别记录前置检查，再调度对应 Turbo 图；不能漏掉前置或把子任务结果冒充完整根门禁。修复后执行适用的原门禁确认最终结果。
- 使用本地 Turbo 的 `--continue=dependencies-successful` 继续独立任务；依赖失败的任务记为阻塞，不用 `--continue=always` 读取旧 `dist` 验收。根 `test` 按 manifest 的 Testcontainers 依赖分类：未声明该依赖的包并发上限 4，声明该依赖的包上限 1；每组启动前再按两个文件 worker 的 CPU 预算和每包 2 GiB 空闲内存预算收紧实际并发，最低为 1，并记录实际值。真实容器测试须声明该测试依赖，包括通过其他包 helper 启动容器的测试。两组顺序运行，避免不同任务图同时重写共享构建产物。浏览器独立配置组失败后继续收集其他组，中断时停止；各组隔离数据与证据。typecheck 也可能触发依赖构建，不与清理/重写相同产物的任务并行。
- 需要强制实际执行时使用 `--force`；本地 Turbo 的 `--no-cache` 仍可能读缓存，不能据此宣称已重新运行。复用结果须符合分轮规范的输入未变条件；真实运行验收不能由缓存代替。

仓库 GitHub CI 按[阶段与复用说明](../../docs/ci.md)运行：不同runner可并行，同工作区共享产物仍串行。main仅在输入指纹、UTC日期及runner镜像/Node身份一致并有独立成功记录时复用；不得将缓存恢复、跳过、取消或旧串行日志直接标为本轮通过。修改workflow、Vitest收集范围或阶段输入归属时同步守卫、测试和说明；保留最终必需汇总，不能因局部修复绕过失败阶段。

测试验证可观察行为，避免为措辞、纯格式修改新增镜像测试。TDD 的 Red 阶段要求新增目标用例因目标行为缺失而失败，既有回归应保持通过。

修复本次引入的失败；已有问题、环境阻塞或未执行项明确报告，不能标成通过。最终说明改动、依据、门禁结果、已同步文档/依赖方、未验证边界。纯文档修改明确无运行时代码影响。验收报告、测试日志与截图保存在被 Git 忽略的 tmp/ 或 test-results/ 中，不提交到 Git。
