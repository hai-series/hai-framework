# 模块审查

审查数据结构参考时，检查每张表、每类缓存值、文件记录和主要接口/运行时对象是否同时有结构说明与示例数据；逐项核对真实字段、时间单位、关联标识与脱敏，字段投影必须明示。缺少示例与结构不符均列为文档问题，按[模块文档规范](../../instructions/module-documentation.md)修正。 先讲每类数据解决什么问题、谁读写、何时清理；每份示例解释业务状态和关键值。不能以 CAS/TTL 等实现词或无注解 JSON 代替用途，配额要说明周期、满额及恢复，详见同一文档规范。

## 能力契约

| 项目 | 契约 |
| --- | --- |
| 能力 | 审查 hai-framework packages 模块的公共契约、生命周期、性能、安全与使用文档 |
| 适用场景 | 框架模块审查、修复评估或仅审查模块文档 |
| 输入 | 明确模块范围、源码入口、调用方、测试和文档 |
| 输出 | 带位置、证据、优先级、影响和验收条件的问题清单 |
| 限制 | 只读审查不自动修改；按模块类型判断 HaiResult/throw 例外，不把内部实现约定强加给调用方。 |

## 使用路径

按 [hai-change-plan](../hai-change-plan/SKILL.md) 核对实际差异及人工确认依据。修复若触发确认要求，取得用户对具体方案与影响的确认后再改。审查时逐项指出缺失的确认、超出获准范围的改动及待同步文档。

问题表达遵循[审查报告与变更影响评估](../../../packages/cli/templates/skills/hai-app-create/collaboration.md#审查报告与变更影响评估)。每项先讲读者看到的影响，再用代码和示例数据对照修改前后，并标明验证依据。

只审查文档时，直接读[模块文档规范](../../instructions/module-documentation.md)和[文档审查步骤](review.md#readme-信息结构与事实核验)。对照源码、调用方和测试核对文字与示例，按文档影响选门禁。

审查配置页时逐项追到真实配置文件和读取者；函数/工厂参数、运行时依赖、UI props 与接口响应应分别归功能或数据参考，不能因字段叫 config 或有 Schema 就认作文件配置。

审查功能页时逐文件、逐大功能检查「用途 → 四级接口清单 → 四级场景」和五列清单。依次比对实际签名、参数列和复杂选项字段表。每个参数须说明作用，复杂选项须说明默认值、生效条件并用具体输入核对输出。单独阅读代码块，检查每次公共调用旁的实参、结果和失败处理。核对同页锚点和三语分组，详见[功能文档要求](../../instructions/module-documentation.md#功能清单与场景示例)。

逐模块识别复杂接口是否缺少合适的流程、时序、状态或职责图。核对图的执行者、顺序、可选分支、受理/完成区别、失败和清理，图旁须解释输入与结果；同步三语并查看桌面/窄屏实际呈现，按[辅助图要求](../../instructions/module-documentation.md#复杂接口与辅助图)验收。

1. 用 rg 确认 package.exports 条件/子路径、入口选择、配置、真实消费者、测试和文档；按生命周期、纯函数、工厂或组件区分契约。构建后用 generate:api/check:api/test:api 核实实际产物、声明、导入和浏览器隔离，不把源码 export 当作已发布 API。
2. 沿调用链核对输入、错误、状态、资源清理和并发，依据当前代码和公开类型判断，不套用统一 init/close。共享数据库租约须核验最终 SQL 的存储端执行时钟，增加节点时钟偏差和真实行锁跨期限证据；本机 Date.now、先查时间或续租成功不能证明最终授权有效。
3. 使用相邻审查表定位风险；内部异常、SQL 片段、缓存和串行操作按实际边界判断，避免机械误报。运行功能默认按 `<模块名>.xx` 进入，核对[入口约定与例外](../../instructions/module-conventions.md#模块功能入口)。按[文档审查步骤](review.md#readme-信息结构与事实核验)核对三语 README、三类模块参考页、代码示例和源码注释。
4. 已授权修复时按影响同步实现、调用方、测试、文档与 skills。按 [工作规范](../../instructions/workspace.md#验证与交付) 分轮收集适用门禁，普通失败先记录，归并问题后集中修复、再验证。
5. 报告位置、优先级、证据、影响、验收与未验证项，不以覆盖率或静态检查替代实际行为。
